# M8 plan: desktop release

Milestone M8 of `architecture.md` §10: `release-desktop.yml` builds the two executables of A20
(the GUI `transcribe-ui-gui` with Qt, the CLI `transcribe-ui` without) for each of the four
platforms, smoke-tests both builds on their own OS and, on `main`, publishes the eight files as
a GitHub Release. It serves `docs/human/requirements.md` "Architecture and code quality" (desktop
stack: PySide6, PyInstaller one-file, static LGPL ffmpeg bundled, unsigned builds for four
platforms; two executables per platform, eight files; on push to `main` build executables and
create a GitHub Release) and the CI rules of `working-agreements.md` "Git and CI" (release builds
only when relevant code changed, no release from a pull request, only the executables uploaded).
The design it builds on: `architecture.md` §8 (CI/CD), §3.1 (the two entry points, "Language of
the texts"), §3.4 (the ffmpeg/ffprobe resolution order, `media/tools.py` `bundle_dir`), §3.8
(Alembic environment as package data), `tooling.md` "Translations" and "CI/CD" (PyInstaller
notes, the language-restart check), `research/desktop-packaging.md` and
`research/desktop-release.md`.

M8 starts once M6 is built (the GUI it packages). It needs no Runpod call, so it does not wait
for M7. Nothing in M8 starts anything on Runpod.

Open questions: A23 (shape of the macOS GUI file; M8.4), A24 (who runs the manual acceptance;
M8.5's "built" mark) and Q36 (the app icon; M8.3). Each has a proposed default, and every part
that does not depend on them can proceed.

## 1. Decisions taken for M8

The part that implements a decision writes it into `architecture.md` (§2, §8) or `tooling.md`;
this plan changes afterwards only by the **(built)** markers.

### Packaging tool

- **PyInstaller, one-file**, as the requirements fix ("Desktop stack *(accepted proposal)*") and
  §8 already says. Nuitka was compared in `research/desktop-packaging.md` §2 (slower builds,
  PySide6 onefile caveats on macOS); not reopened.
- **No `.spec` file.** `scripts/build_desktop.py` composes the PyInstaller command line per
  variant and platform and runs `pyinstaller` as a subprocess. A script is linted, typed and
  tested like the other `scripts/`; a `.spec` is Python that no linter sees. Project hooks live
  in `apps/desktop/packaging/hooks/` (`--additional-hooks-dir`), as linted `.py` files.
  Architecture §2's "PyInstaller spec" becomes "packaging hooks and templates".
- **Build environment**: a `packaging` dependency group of `apps/desktop` (PyInstaller, Pillow
  for the icon); the build runs in
  `uv sync --locked --no-dev --no-editable --package transcribe-ui --group packaging`, so no dev
  tool can leak into a bundle and the app is analysed as an installed, non-editable
  distribution (its metadata present for `importlib.metadata`).
- **Options for both variants**: `--onefile`, `--noupx` (UPX raises antivirus hits), `--clean`,
  `--copy-metadata transcribe-ui` (the version comes from the metadata, §"Version stamping"),
  `--copy-metadata keyring` and `--collect-submodules keyring.backends` (`tooling.md`),
  `--collect-submodules transcribe_ui` (the GUI entry imports `transcribe_ui.gui.app` through
  `importlib`, which the analysis cannot follow; collecting the package also covers the request
  handlers in the route table).
- **CLI variant**: console; excludes `PySide6`, `shiboken6` and `transcribe_ui.gui` (its submodule
  collection filters `transcribe_ui.gui` out). The CLI's own import test (§3.1) already keeps Qt
  out of its import graph; the exclusion and the `cli-bundle` check (below) make a leak fail the
  build instead of bloating it.
- **GUI variant**: windowed on Windows (`--windowed`, the GUI subsystem). On macOS the shape
  follows A23 (proposed: a onedir `.app` in a `.dmg`; with the bare-file option, a console-mode
  one-file binary without `BUNDLE`, since PyInstaller deprecates one-file `.app` bundles and will
  block them in 7.0). On Linux a plain one-file binary. Only the QtCore, QtGui and QtWidgets
  modules the app imports are collected (`pyside6-essentials` already has no WebEngine); QtTest
  is excluded.

### Platforms and runners

- **Windows x64**: `windows-2025`, as CI's Windows leg.
- **macOS arm64**: `macos-15` (pinned: `macos-latest` moved to macOS 26).
- **macOS x86_64**: `macos-15-intel`, the only Intel label left; GitHub ends x86_64 macOS
  runners when the macOS 15 image retires (fall 2027, `research/desktop-release.md`). Two
  binaries rather than `universal2`: every native dependency would need universal wheels.
- **Linux x64**: built on `ubuntu-24.04` inside the `quay.io/pypa/manylinux_2_34_x86_64`
  container (AlmaLinux 9, glibc 2.34; pinned by digest), smoke-tested on the host and again in an
  `ubuntu:22.04` container (the oldest Ubuntu LTS the build supports). Reason: §8's
  `ubuntu-22.04` runner is deprecated since 2026-09-17 and unsupported from 2027-04-17, and
  PySide6 6.12's Linux wheel needs glibc 2.34 anyway, so the manylinux 2.34 image gives the widest
  reach the dependencies allow and does not depend on a runner image's life.
- **Minimum OS versions** (written into the release notes): Windows 10 1809 or later (Qt 6),
  macOS 14 or later (PySide6 6.12's wheel), Linux with glibc 2.34 or later (for example Ubuntu
  22.04, Debian 12, Fedora 35, RHEL 9). The floors are what the wheels require; only Ubuntu 22.04
  is run in CI.
- **Python**: uv-managed CPython 3.13 (`.python-version`), the same interpreter as CI.
- Out of scope: Windows and Linux on arm64 (not in the requirements; the platform list is
  four).

### What goes into each build

- **Catalogs**: `transcribe_ui/locale/**/*.mo` as data of the `transcribe_ui` package (both
  variants), where `i18n/catalog.py` finds them through `importlib.resources`. The `.po` and
  `.pot` files are not bundled.
- **Alembic environment**: `transcribe_ui/state/migrations/` (`env.py`, `script.py.mako`,
  `versions/*.py`) collected as data with its `.py` files (`collect_data_files(...,
  include_py_files=True)` in the project hook): Alembic loads the revisions as files from that
  folder (`state/upgrade.py` `as_file`), not as imported modules. Both variants, since both open
  the database.
- **Qt**: the platform plugins (Windows `qwindows`, macOS `qcocoa`, Linux `xcb` and `wayland`,
  and `offscreen` everywhere), image formats and styles the PySide6 hooks collect, and Qt's
  `qtbase_hu.qm` (§3.1: without it Qt's own buttons stay English). The GUI's bundle check
  (below) names each, so a hook change that drops one fails the build.
- **ffmpeg and ffprobe**: §"ffmpeg" below, added with `--add-binary` at the bundle's root, where
  `media/tools.py` `bundle_dir` (`sys._MEIPASS`) already looks; both variants (the CLI needs them
  for `review_batch` and `run_upload`).
- **Build stamp**: a generated `version.txt` (§"Version stamping").
- **Third-party notices**: a generated `THIRD_PARTY_NOTICES.txt` (M8.3).
- **Windows version resource** (`--version-file`, generated): product name "Transcribe-UI",
  file description per variant, numeric file version from the base version, product version the
  stamped version, original file name. It shows in the file's properties and reduces antivirus
  heuristics on unknown executables.
- **Icon** (Q36): `.ico` on Windows, `.icns` in the macOS `.app`, and the Qt window icon on every
  OS; the Linux one-file binary carries none (desktop files are out of scope).

### ffmpeg

- **Built by us from the pinned upstream source**, the same version and configure flags on all
  four platforms: `scripts/build_ffmpeg.py` downloads `ffmpeg-<version>.tar.xz`, checks its
  SHA-256 against the value committed next to the version (computed once from the release whose
  PGP signature was verified, recorded in `research/desktop-release.md` when pinned), and
  configures an LGPL build: no `--enable-gpl` or `--enable-nonfree`, `--disable-autodetect` (no
  system library is picked up), static, only the `ffmpeg` and `ffprobe` programs, no network, no
  documentation, devices disabled except the `lavfi` input (the desktop's media tests generate
  their media with it), every native decoder, demuxer, parser, muxer and filter kept (the probe
  must know every container a user has). macOS builds set the deployment target to 14.0; the
  Windows build is cross-compiled on Linux with mingw-w64; Linux builds in the same manylinux
  container as the app.
- Why not downloaded builds: no single source offers LGPL builds for all four platforms (BtbN has
  none for macOS, evermeet.cx is x86_64 and GPL), BtbN's assets are rolling (a pinned URL
  disappears), and different builds would behave differently per OS. One configure line also
  gives one licence statement and one source offer (the upstream tarball and the script in this
  public repository).
- **Checked before bundling**: `ffmpeg -L` reports LGPL; the desktop tests that run the real
  binaries (`test_media_ffmpeg.py`, `test_batches_ffprobe.py`) pass with the built tools first
  on `PATH`, on each build leg (for Windows, on the Windows leg).
- The version pinned is the newest FFmpeg release when M8.2 starts (9.1 on 2026-11-28); later
  bumps are a one-line change plus the new checksum.

### Version stamping

- The base version stays `[project] version` of `apps/desktop/pyproject.toml` (now 0.1.0),
  changed by hand in a PR when the architect wants a new number; `uv.lock` follows.
- A release build's version is `<base>+<YYYYMMDD>.<short sha>` (a PEP 440 local version; the
  date is the commit's committer date in UTC, so every leg and any re-run agree). The build
  script writes it to `version.txt`, bundled as data of `transcribe_ui`; `api/info.py`
  `app_version()` returns it when that resource exists, else the metadata version. So
  `--version` (`transcribe-ui 0.1.0+20261128.abc1234`), `get_app_info`, the About page and the
  window title all show the build. From source nothing changes (no such file in the
  repository), so goldens keep `0.1.0`.
- macOS `.app` (A23 default): `CFBundleShortVersionString` the base version, `CFBundleVersion`
  the date as `YYYY.MM.DD` (Apple requires up to three integers), `CFBundleIdentifier`
  `io.github.markfazekas.transcribe-ui`, `LSMinimumSystemVersion` 14.0,
  `NSHighResolutionCapable`.

### Trigger, pull request checks and release

- `release-desktop.yml` runs on pull requests and pushes to `main` that touch
  `apps/desktop/**` (except `apps/desktop/tests/**`: a test-only change builds nothing new),
  `packages/contracts/**`, `uv.lock`, `pyproject.toml`, `.python-version`, the build, ffmpeg,
  smoke and release scripts, or the workflow itself; and on manual dispatch. Like
  `release-worker.yml`: concurrency per ref, superseded pull request runs cancelled, a run on
  `main` never cancelled (a newer push only replaces a queued one, so releases appear in commit
  order).
- **Pull requests build and smoke-test all eight files and publish nothing.** The release job
  runs there in dry mode: it downloads the eight artifacts, checks the exact file set, renders the
  release notes into the job summary and stops before `gh release create`. The workflow is not a
  required check (a path-filtered workflow cannot be one without blocking unrelated pull
  requests); as with `release-worker.yml`, the main session merges a pull request that triggered
  it only when its run is green.
- **How the smoke tests are proven before the first release**: the pull request that adds the
  workflow (M8.1) runs it on its own branch, so all four legs build and pass their smoke tests
  before it merges; until M8.5 the workflow has no release job, so its runs on `main` build and
  smoke-test without publishing; M8.5's pull request runs the release job in dry mode. The first
  real release is the run of M8.5's merge.
- **Release** (only for a push to `main` or a dispatch on `main`; `permissions: contents:
  write` on that job alone): needs every build leg, so it runs only when all eight builds and
  their smoke tests passed. Tag `desktop-<YYYYMMDD>-<short sha>` on the commit, title
  `Transcribe-UI <version>`, the eight files, notes from a template
  (`apps/desktop/packaging/release-notes.md`): version and commit, minimum OS versions, first
  start per OS (Windows SmartScreen "More info" then "Run anyway"; macOS quarantine and, per
  A23, the "Open Anyway" button in System Settings or `xattr -d com.apple.quarantine`; Linux
  `chmod +x` and the system libraries Qt needs), the SHA-256 of each file, and the third-party
  licences with the FFmpeg source and configure line. Checksums go in the notes, not in a file:
  only the executables are uploaded.
- **Re-runs**: a published release with the same tag and exactly the eight expected files ends the
  job successfully without a change (a dispatch on an already released commit); a leftover draft
  with that tag (an upload failed half-way) is deleted and created again; a published release
  with a different file set fails the job (a human looks).
- **Pre-release until M7 is built**: the cloud path has not had a real run yet, so releases are
  marked pre-release (GitHub's "latest" link skips them); M7's completing PR removes the flag
  from the workflow. Old releases are kept (each is the build of one commit; storage is free for
  a public repository); revisit if the list gets unwieldy.

### Artifact naming

- `transcribe-ui-<os>-<arch>-<variant>` with `<os>` `windows`, `macos`, `linux`, `<arch>` `x64`
  or `arm64`, `<variant>` `gui` or `cli`, plus `.exe` on Windows; per A23's default the macOS
  GUI files are `transcribe-ui-macos-arm64-gui.dmg` and `transcribe-ui-macos-x64-gui.dmg`
  (holding `Transcribe-UI.app`). No version in the file name, so a download link to the latest
  release stays the same. The build produces these names directly (PyInstaller `--name`), so the
  smoke tests run the file that is published.
- Each file is uploaded on its build leg with `actions/upload-artifact@v7` `archive: false`
  (one step per file; 7-day retention, so the files of a pull request run can be downloaded and
  tried by hand); the release job downloads them. Nothing else is uploaded: the ffmpeg builds
  travel between jobs through the cache, not as artifacts.

### Signing and notarization

- **Out of scope**: the requirements accepted "unsigned builds for four platforms". Consequences
  the release notes state: SmartScreen warns on Windows; macOS quarantines downloaded files
  (arm64 binaries still get PyInstaller's ad-hoc signature, which Apple Silicon requires);
  the macOS keychain may ask again for access after an update, since an ad-hoc signed build has
  a new identity each time. Signing is an idea for later (Azure Trusted Signing or SignPath for
  Windows, a Developer ID with notarization for macOS), not planned.
- The stock PyInstaller bootloader is used. Rebuilding it from source (a common antivirus
  mitigation) is done only if Defender flags a build (the Windows smoke run, with Defender
  active, would show it).

### Caching

- uv's cache through `astral-sh/setup-uv` `enable-cache` (keyed on `uv.lock`), per OS, as in CI.
- ffmpeg: an `ffmpeg` job (one leg per platform) looks up the key
  `ffmpeg-<version>-<os>-<arch>-<hash of scripts/build_ffmpeg.py>` with `lookup-only`, builds
  and saves only on a miss (`enableCrossOsArchive` on the Windows entry, which is built on
  Linux); each build leg restores its entry with `fail-on-cache-miss`. A cache hit costs seconds;
  a miss about 10 to 20 minutes per platform [I]. The job runs on every workflow run, so an entry
  evicted after a week unused is rebuilt before a build leg needs it.
- Not cached: PyInstaller's `build/` and `dist/` (a fresh analysis each run; a stale analysis is
  a correctness risk, and a build takes minutes), the manylinux image (pulled per run).

### Smoke tests

`scripts/smoke_desktop_build.py <cli> <gui> --version <expected>` runs on each build leg after the
build and before the upload, prints one line per check and a summary (sizes, the CLI's cold
start time) to the job summary, and on a failure prints the app's log file. Every check has a
timeout (generous on Windows, where Defender scans the unpacked files); a check that times out
kills the process tree and fails. The CLI checks run first, on fresh per-user state, with `PATH`
stripped of any folder holding `ffmpeg` or `ffprobe`, so only the bundled tools can answer.

- `cli-version`: `<cli> --version` exits 0 and prints exactly `transcribe-ui <expected>`.
- `cli-database`: `<cli> run -` with `{"action": "list_batches"}` exits 0 with status `ok`: the
  fresh database was created and migrated, so the bundled Alembic environment works.
- `cli-probe` (from M8.2): in a temporary folder, a one-second WAV written with the standard
  library's `wave`; the requests that scan it, create a batch and review it (the first probing
  request, `review_batch`) answer `ok` with the file's duration: the bundled ffprobe is found
  through `sys._MEIPASS` and runs.
- `cli-help-hu`: on Linux, `LANGUAGE=hu <cli> --help` exits 0 and its output contains the
  Hungarian text of "print the app version and exit", read at smoke time from the repository's
  `hu` catalog with the standard library's `gettext` (and different from the English one, so a
  missing catalog cannot pass). On Windows and macOS, where the OS language is not read from the
  environment, the same check after the `language` setting is set to `hu` through
  `get_settings`/`update_settings` (so the GUI checks after it also run in Hungarian, loading
  `qtbase_hu.qm`). This is §10's Linux check plus the same catalog check on the other platforms.
- `cli-bundle`: the CLI's archive listing contains the `en` and `hu` `.mo` files, the Alembic
  `env.py` and every file of `versions/`, `version.txt`, the notices (from M8.3) and ffmpeg and
  ffprobe (from M8.2), and no `PySide6`, `shiboken6` or Qt library.
- `gui-bundle`: the GUI's listing (for the `.app`, its `Contents` folder) contains the same plus
  `qtbase_hu.qm` and the `offscreen` and native platform plugins.
- `gui-offscreen`: `QT_QPA_PLATFORM=offscreen` and `TRANSCRIBE_UI_SMOKE_TEST=1`: the GUI exits 0
  by itself (§"GUI smoke mode").
- `gui-native`: the same with the native platform: Windows and macOS on the runner's desktop
  session, Linux `xcb` under `xvfb-run`. It proves the native platform plugin and its libraries,
  which the offscreen start never loads. If a runner turns out to have no usable desktop
  session, that platform keeps only `gui-offscreen`, and architecture §8 says so.
- `linux-floor` (Linux leg only): in an `ubuntu:22.04` container with only the libraries the
  release notes list installed, `cli-version`, `cli-database` and `gui-offscreen` pass.

### GUI smoke mode

- With `TRANSCRIBE_UI_SMOKE_TEST=1` (a constant in `gui/constants.py`), `run_gui` passes an
  `on_window` hook (the existing test seam) that waits until every start-up step has answered,
  logs each step's outcome, closes the window through the normal close handling (nothing is in
  flight then; the set-up wizard, open because no R2 credential exists, closes with it) and makes
  the exit code 0 when every start-up request answered `ok`, else 1. A missing credential or an
  unusable keyring is an `ok` answer of `credentials_status`, so a fresh CI machine passes.
- Without the variable nothing changes. A user who sets it only gets a GUI that quits after
  start-up; no other behaviour hangs on it.

### Manual acceptance (A24)

A short checklist per OS on the first release, beyond what CI can click: start from the file
manager (double-click), the window and its icon, the first-start wizard, store and test
credentials (the keyring of the real desktop), change the language and "Restart now" (the new
window opens in the new language; Windows may only flash it in the task bar, `tooling.md`),
`transcribe-ui --version` and `--help` in a terminal, and the CLI's `credentials` prompt.

## 4. Risks

- **uv's Python under PyInstaller**: the python-build-standalone interpreter must provide the
  shared `libpython` PyInstaller bundles (the manylinux image's own Pythons are static and cannot
  be used). M8.1 finds out on the first run; the fallback is an interpreter from
  `actions/setup-python` (or the distribution's `python3.13` in the container) given to
  `uv venv --python`.
- **Missing hidden imports or data** (SQLAlchemy dialects, Alembic, botocore data, keyring
  backends, Qt plugins): each shows up as a failing smoke check (`cli-database`, `gui-native`,
  the bundle lists), not in users' hands; fixed in the project hooks.
- **One-file start time**: every start unpacks the bundle, ffmpeg included (two static
  executables, tens of MB each), so the CLI's cold start is slower than from source and slower
  still under Windows Defender. The smoke summary records it per platform; if it is too slow,
  the fallback is a shared-library ffmpeg (one set of libraries for both programs, about half
  the size), not dropping the bundle.
- **Linux desktop libraries**: Qt's `xcb` plugin needs libraries a minimal system lacks
  (`libxcb-cursor0` and friends). `gui-native` under Xvfb and `linux-floor` show which ones the
  build does not bring itself; the release notes list them.
- **Runner retirements**: `macos-15-intel` ends with the macOS 15 image (fall 2027); then the
  x86_64 macOS build needs another route (an x86_64 Python under Rosetta on an arm64 runner) or
  is dropped (an architect question at that time). The Linux build no longer depends on a
  runner's Ubuntu version.
- **Native GUI start on runners**: if a hosted runner's session cannot show a window, that
  platform keeps only the offscreen start (§1 "Smoke tests"), and the manual acceptance carries
  the native check.
- **macOS without a Mac at hand** (A24): the language restart and the double-click start are
  then verified only on Windows and Linux.
