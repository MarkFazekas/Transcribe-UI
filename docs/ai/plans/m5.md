# M5 plan: desktop backend

Milestone M5 of `architecture.md` §10: the desktop backend behind one façade, reachable from a
thin JSON CLI, verified by flow tests against `moto` S3 and a fake Runpod API. It serves
`docs/human/requirements.md` sections "UI app: file selection", "UI app: review step", "UI app:
conversion and upload", "Batches", "Cloud cleanup", "Subtitle download options", "Runpod
control", "Failure handling" (desktop side) and "Architecture and code quality"; the design is
`architecture.md` §3.1-3.7, §4 (R2 layout contract, desktop as writer), §6, §7 ("Desktop flow
tests"), §8 (`ci.yml`). Packaging is M8, the GUI and CLI ergonomics are M6, real Runpod runs
are M7.

## 1. Decisions taken for M5

Conventional defaults where the docs leave a gap. The part that implements a decision writes it
into `architecture.md`; this plan changes afterwards only by the **(built)** markers.

- **Thin CLI in M5.** `transcribe-ui run <request.json>`, `transcribe-ui schema` and
  `--version` are built in M5.1, because §7 flow tests run every request through the CLI entry
  point too. Argparse (no extra dependency). M6 adds the GUI, the interactive credential prompt
  polish and human-readable progress. Exit codes: 0 success, 1 error response, 2 request file
  invalid (the error response is still printed as JSON).
- **Request/response models live in the desktop app** (`transcribe_ui/api/classes.py`), not in
  `packages/contracts`: §2 keeps contracts for code shared with the worker. Their JSON Schema
  snapshots live in `apps/desktop/tests/snapshots/`; M5.1 rewords §7 "Contract tests"
  accordingly.
- **Confirmations are data.** A request that needs a confirmation (existing-language warning
  on `create_batch`, cost estimate on `launch_worker`, `cleanup_cloud`, overwrite on
  `run_download`) is answered with a `needs_confirmation` response listing what to confirm and
  changes nothing; the same request with the confirmation field set performs it. One pattern,
  so GUI, CLI and MCP behave the same.
- **Machine-dependent inputs are request fields.** Scan options (included extensions, hidden
  entries) and placement options are fields of the request with defaults; the GUI fills them
  from the settings. The settings file is read only by `get_settings`/`update_settings` and by
  the GUI, so the same request JSON gives the same response everywhere (§3.1).
- **Composition is persisted.** Requirements "Batches" asks every step, phase 1 included, to be
  resumable: `create_batch` stores the batch in `composing` (batch id from the injected clock),
  `edit_batch` replaces its items while in `composing`, `start_review` moves it to `reviewing`.
  A batch in `composing` can be deleted (`delete_batch`); later phases cannot.
- **One SQLAlchemy schema, owned by `state/`.** All tables live in `state/models.py` (the app
  has one SQLite file); rows keep Pydantic payloads as JSON plus indexed status columns (§3.3),
  so most later parts change only payload classes, not tables. Until the first desktop release
  (M8) no user database exists: the schema stays one initial Alembic revision that parts edit in
  place (developers delete their local DB), which avoids parallel Alembic heads. From M8 on,
  every change is a new revision.
- **Dependencies up front.** M5.1 adds every runtime dependency M5 needs to
  `apps/desktop/pyproject.toml` (pydantic, sqlalchemy, alembic, platformdirs, keyring, httpx,
  boto3), so parallel parts do not conflict on `uv.lock`. No new dev dependency: HTTP fakes
  use `httpx.MockTransport`, S3 uses the existing `moto`.
- **Concurrency inside the process.** `Backend.execute` is safe to call from several threads
  (the GUI will): a SQLAlchemy session per request; long commands (`review_batch` probing,
  `run_upload`, `run_download`, `cleanup_cloud`) take an in-process lock per batch and refuse
  with `batch_busy` instead of waiting; `launch_worker`, `cancel_worker`, `reconcile_cloud`
  and `refresh_status` share one runs lock. The cross-process writer lock (§3.3) is taken when
  the backend opens the database; a second process gets `app_busy`.
- **Cancellation.** `execute` takes a `CancelToken` next to the `ProgressSink`; long commands
  check it between items and between multipart parts and stop with `cancelled` after persisting
  what is done. CLI: Ctrl+C sets it, a second Ctrl+C exits at once (state is consistent either
  way: every step is idempotent). Re-sending the request resumes.
- **Upload resume granularity.** An interrupted object is uploaded again from its start; parts
  are not resumed across processes. Stale multipart uploads under the batch prefix are aborted
  when `run_upload` starts. Temp audio is one file at a time in `user_cache_dir`, removed on
  start-up of the next `run_upload` if left over.
- **Partial results.** `plan_download` accepts batches in `transcribed` (and extract-only
  batches); jobs already finished while the batch is `ready` are shown by `refresh_status` but
  not placed before `_done.json`, as the requirements' phase 4 says.
- **Run deadline and wait.** The wait for a machine is 5 min to 7 days (default 1 h, §3.7).
  `MAX_RUNTIME_S` = start-up allowance (20 min) + per transcribe job the worker's own timeout
  rule (§5.3: max(10 min, 1 s per audio second), doubled for `careful`), capped at 24 h; test
  mode uses 2 h and `KEEP_POD_ALIVE=true` (requirements "Deployed app"). The pod name deadline
  (`transcribe_contracts.pods`, M3) = queue `expiresAt` + `MAX_RUNTIME_S` + 10 min. Constants in
  `runs/constants.py`, recalibrated at M7.
- **Cost estimate.** Range = price per hour × (start-up 5-20 min + total transcribe-job audio
  duration × real-time factor 0.05-0.20), `careful` jobs counted twice. Price from
  `GET /v2/catalog/gpus` (read-only, secure price of `NVIDIA RTX A5000`), falling back to a
  constant (0.27 USD/h) with a note in the response. The factors are [I] and recalibrated at M7.
- **Cloud setup is idempotent and explicit.** `setup_cloud` creates or updates, by fixed
  names, the Runpod secrets holding the R2 credentials, the Global Volume
  (`transcribe-ui-backups`) and the template (image
  `markfazekasgh/transcribe-ui-worker:schema-<contracts major>`, `startSsh`/`startJupyter`
  false, Global Volume at `/workspace`, non-secret env, secret env as
  `{{ RUNPOD_SECRET_<name> }}`). `launch_worker` refuses with `cloud_not_set_up` until it ran.
  A separate pods-only terminate key (§5.2, decided by M4) is an optional secret the template
  builder already supports, off by default. Open as A18 (which R2 token the pod gets).
- **R2 adapter is the desktop's own.** The worker's `pipeline/storage.py` is not shared (apps
  share only contracts); the desktop adapter follows the same boto3 settings (§6) and adds
  `head`, `copy`, `delete`, multipart abort and upload with progress.
- **Golden files.** Responses are compared after replacing the test's temp root with
  `<root>`; clock, ULID randomness and fakes are fixed, so the remaining JSON is byte-identical.
  Progress events are golden too (NDJSON).

## 2. Package layout

`apps/desktop/src/transcribe_ui/`, Django-like (each sub-package with `constants.py` and
`classes.py` where it has constants or Pydantic models; logic in named modules):

- `api/`: `classes.py` (the `Request`/`Response` discriminated unions, `ErrorResponse`,
  `NeedsConfirmation`, `ProgressEvent`), `errors.py` (`DomainError` with a code), `backend.py`
  (`Backend.execute`, dispatch table), `ports.py` (`Clock`, `IdSource`, `ProgressSink`,
  `CancelToken`), `wiring.py` (composition root: real adapters for the CLI, fakes for tests).
- `state/`: `paths.py` (platformdirs, injectable root), `database.py` (engine, WAL, sessions,
  migrations at start-up), `locks.py` (writer lock file, per-batch and runs locks),
  `models.py`, `migrations/` (`env.py`, `script.py.mako`, `versions/`), `settings.py`,
  `logs.py` (human-readable log + rotating file in the user log dir).
- `discovery/`: `scan.py`, `sidecars.py`, `languages.py`, `filters.py`, `selection.py`.
- `media/`: `tools.py` (ffmpeg/ffprobe resolution), `probe.py`, `convert.py`, `extract.py`,
  `fake.py`.
- `credentials/`: `store.py` (keyring + environment fallback), `services.py`.
- `storage/`: `r2.py` (`ObjectStore` protocol + boto3 adapter).
- `runpod/`: `client.py` (typed httpx v2 client), `fake.py` (fake API on `MockTransport`),
  `setup.py`, `reconcile.py`.
- `batches/`: `services.py` (create/edit/delete/list/get/hide), `review.py`, `phases.py`.
- `upload/`: `services.py`, `manifest.py`.
- `runs/`: `estimate.py`, `launch.py`, `monitor.py`.
- `placement/`: `naming.py`, `planner.py`, `custom.py`, `writer.py`.
- `cleanup/`: `services.py`.
- `cli/`: `main.py` (entry point `transcribe-ui`).

Tests in `apps/desktop/tests/` (flow tests per area, `support/` helpers: parity runner, golden
files in `tests/golden/`, media generator, moto fixture, fake Runpod).

## 5. Risks

- Windows CI leg: ffmpeg availability and path/locking differences (`os.replace` onto an open
  file, SQLite file locks). Found early by M5.1/M5.2 on `windows-2025`.
- moto does not reproduce R2's checksum behaviour (research/desktop-packaging.md §4); an
  `integration`-marked R2 test with the real bucket runs locally before M7.
- Runpod v2 details the fake encodes (queue 202 body, secret syntax in templates, catalog
  shape) are from the OpenAPI spec, not from a real call; M4/M7 verify them, the fake is updated
  then.
- Cost and runtime constants are guesses until M7 measures a real run.
