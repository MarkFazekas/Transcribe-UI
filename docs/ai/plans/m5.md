# M5 plan: desktop backend

Milestone M5 of `architecture.md` §10: the desktop backend behind one façade, reachable from a
thin JSON CLI, verified by flow tests against `moto` S3 and a fake Runpod API. It serves
`docs/human/requirements.md` sections "UI app: file selection", "UI app: review step", "UI app:
conversion and upload", "Batches", "Cloud cleanup", "Subtitle download options", "Runpod
control", "Failure handling" (desktop side) and "Architecture and code quality"; the design is
`architecture.md` §3.1-3.7, §4 (R2 layout contract, desktop as writer), §6, §7 ("Desktop flow
tests"), §8 (`ci.yml`). Packaging is M8, the GUI and CLI ergonomics are M6, real Runpod runs
are M7.

Open questions the plan is written on (their proposed defaults): Q23-Q28
(`questions-for-product.md`), A18-A19 (`questions-for-architect.md`). An answer that differs
changes the part that implements it.

## 1. Decisions taken for M5

Conventional defaults where the docs leave a gap. The part that implements a decision writes it
into `architecture.md`; this plan changes afterwards only by the **(built)** markers.

### Façade and CLI

- **Thin CLI in M5.** `transcribe-ui run <request.json>`, `transcribe-ui schema` and
  `--version` are built in M5.1, because §7 flow tests run every request through the CLI entry
  point too. Argparse (no extra dependency). M6 adds the GUI, the interactive credential prompt
  polish and human-readable progress. The response is printed as JSON in every case (UTF-8,
  `\n` line ends on every OS). Exit codes:
  - 0: success;
  - 1: error response;
  - 2: request file invalid;
  - 3: `needs_confirmation` (nothing was changed);
  - 130: `cancelled` (Ctrl+C; what was done is persisted).
- **Request/response models live in the desktop app** (`transcribe_ui/api/classes.py`), not in
  `packages/contracts`: §2 keeps contracts for code shared with the worker. Their JSON Schema
  snapshots live in `apps/desktop/tests/snapshots/`; M5.1 rewords §7 "Contract tests"
  accordingly. On a rebase conflict in a snapshot or golden file, regenerate it
  (`UPDATE_SNAPSHOTS=1`), never merge it by hand.
- **Confirmations are data.** A request that needs a confirmation (existing-language warning
  on `create_batch`, cost estimate on `launch_worker`, `cleanup_cloud`, overwrite on
  `run_download`) is answered with a `needs_confirmation` response listing what to confirm and
  changes nothing; the same request with the confirmation field set performs it. One pattern,
  so GUI, CLI and MCP behave the same.
- **Machine-dependent inputs are request fields.** Scan options (included extensions, hidden
  entries) and placement options are fields of the request with defaults; the GUI fills them
  from the settings. Request handling never reads the settings file: it is read by
  `get_settings`/`update_settings`, by the GUI (to fill request fields) and by the composition
  root (`api/wiring.py`), which reads adapter configuration (the ffmpeg/ffprobe path override)
  when it builds the adapters and injects it. So the same request JSON gives the same response
  everywhere (§3.1).
- **Test mode is a request field.** `launch_worker.test_mode` (default false) sets
  `KEEP_POD_ALIVE=true` and `MAX_RUNTIME_S` = 2 h (requirements "Deployed app"). Not a setting,
  so the request alone decides (§3.1); M6 shows it as an advanced option.
- **Frontend duties (M6).** The GUI runs `reconcile_cloud` at start-up and `refresh_status`
  periodically while a run is active (and once at start-up); the backend has no timer of its
  own. The CLI leaves both to the user.

### State and concurrency

- **Composition is persisted.** Requirements "Batches" asks every step, phase 1 included, to be
  resumable: `create_batch` stores the batch in `composing`, `edit_batch` replaces its items
  while in `composing`, `start_review` moves it to `reviewing`. A batch in `composing` or
  `reviewing` can be deleted (`delete_batch`; nothing is in the cloud yet, Q26). From
  `uploading` on, the way out is `cleanup_cloud` (M5.13).
- **One SQLAlchemy schema, owned by `state/`.** All tables live in `state/models.py` (the app
  has one SQLite file); rows keep Pydantic payloads as JSON plus indexed status columns (§3.3),
  so most later parts change only payload classes, not tables. Until M5 is marked **(built)**,
  the schema is one initial Alembic revision that parts edit in place (developers delete their
  local DB), which avoids parallel Alembic heads. From then on (M7 creates the first data worth
  keeping) every change is a new revision.
- **Dependencies up front.** M5.1 adds every runtime dependency M5 needs to
  `apps/desktop/pyproject.toml` (pydantic, sqlalchemy, alembic, platformdirs, keyring, httpx,
  boto3), so parallel parts do not conflict on `uv.lock`. No new dev dependency: HTTP fakes
  use `httpx.MockTransport`, S3 uses the existing `moto`.
- **Concurrency inside the process.** `Backend.execute` is safe to call from several threads
  (the GUI will), with a SQLAlchemy session per request.
  - Batch lock (in-process, per batch): every request that changes a batch takes it:
    `edit_batch`, `delete_batch`, `start_review`, `review_batch`, `resolve_review`,
    `run_upload`, `run_download`, `import_custom_plan`, `create_retry_batch` (on the source
    batch), `cleanup_cloud`, `set_batch_hidden`. It is never waited for: a held lock gives
    `batch_busy`.
  - Runs lock (in-process, one): `launch_worker`, `cancel_worker`, `refresh_status`,
    `reconcile_cloud`, `terminate_pod`, `cancel_queued_pod`, `cleanup_cloud`, and the manifest
    step of `run_upload` (Q27).
  - Lock order is runs → batch: `cleanup_cloud` takes the runs lock, then the batch lock.
    `run_upload` already holds its batch lock and takes the runs lock only for its manifest
    step, with a bounded wait (`RUNS_LOCK_WAIT_S`, then `runs_busy` after persisting;
    re-sending resumes). Since batch locks are never waited for, no two requests can wait on
    each other.
  - Phase transitions are compare-and-set in one transaction (`UPDATE … WHERE phase =
    :expected`; no row changed → `phase_conflict`), so a request that lost a race changes
    nothing.
  - Writer lock (cross-process, §3.3): taken when the backend first opens the database.
    Request types that need no database (`get_app_info`, `scan_tree`, `preview_selection`,
    `get_settings`, `update_settings`, the credential requests, `setup_cloud`,
    `cloud_setup_status`) are marked so in the dispatch table and never open it, so the CLI can
    run them while the GUI is open; any other request in a second process gets `app_busy`. The
    settings file is written atomically (temp file + `os.replace`); the last writer wins.
- **Cancellation.** `execute` takes a `CancelToken` next to the `ProgressSink`; long commands
  check it between items and between multipart parts and stop with `cancelled` after persisting
  what is done. CLI: Ctrl+C sets it, a second Ctrl+C exits at once (state is consistent either
  way: every step is idempotent). Re-sending the request resumes.

### Upload, download and cleanup

- **Upload.** Audio files are uploaded as they are, straight from the source (§3.4); only
  video items are converted to a temp file first. An interrupted object is uploaded again from
  its start; parts are not resumed across processes. Stale multipart uploads under the batch
  prefix are aborted when `run_upload` starts. Temp audio is one file at a time in
  `user_cache_dir`, removed on start-up of the next `run_upload` if left over.
- **Manifest held back during a run (Q27).** When a batch's last object is verified while a
  run is `launching`, queued or running, `run_upload` keeps the manifest back: the batch stays
  `uploading` with "upload complete, waiting for the current run". `launch_worker` and
  `refresh_status` (both under the runs lock) publish held manifests (→ `ready`) whenever no
  run is active. So a running worker never gets work its `MAX_RUNTIME_S` and cost estimate did
  not include.
- **Download (Q24, Q25, Q23).** `plan_download` accepts batches in `ready` (finished jobs only;
  the others are listed as "not finished yet"), `transcribed` and `downloaded` (again, any
  number of times while the results are in R2; extracted subtitles are in SQLite and always
  available), and extract-only batches. `run_download` records each placed target; it moves a
  `transcribed` batch to `downloaded` once its plan is executed, and leaves the phase of a
  `ready` or `downloaded` batch alone. Jobs without a result after a run ended stay pending: the
  next start transcribes them (the worker processes every manifest without `_done.json`).
- **Cleanup.** `cleanup_cloud` is available from `uploading` on (Q26):
  - From `uploading` (scope `everything` only): abort multipart uploads under the batch prefix,
    delete the uploaded audio and the temp file → `cleaned`. A batch in `uploading` has no
    manifest, so no worker can see it, and this is allowed during a run.
  - `audio` (from `ready` on): refused while a run is active or jobs lack a result (§3.3);
    deletes the audio objects and sets the batch's `audio_deleted` flag. The phase does not
    change, the results stay downloadable. `create_retry_batch` is refused with `audio_deleted`
    afterwards.
  - `everything` (from `ready` on): refused while a run is active; order manifest →
    `_done.json` and results → audio (§3.3), a second confirmation when results were not
    downloaded → `cleaned`.
  - Missing objects are not errors; every stage is resumable.
- **Run objects.** When a run has ended and its pod is gone, `refresh_status` stores the final
  `status.json` in the run row and `worker.log` in the user log dir, then deletes
  `runs/<run_id>/` (a failed delete is retried at the next refresh). The worker is the only
  writer of these objects (§4) and is gone by then.

### Runpod

- **Run scope = the whole `batch_metadata/` prefix.** The worker processes every manifest
  without `_done.json` (§5.3), including manifests this database does not know (another
  computer, a deleted dev DB). `plan_launch` therefore lists `batch_metadata/`, reads each
  pending manifest (`reading.read_manifest`) and sizes the estimate and `MAX_RUNTIME_S` from
  all of them; unknown batches are listed separately (id, files, audio duration) and can be
  deleted from the cloud from there (Q28: `cleanup_cloud` with scope `everything` accepts a
  batch id that has a manifest in R2 but no local row). `refresh_status` checks `_done.json`
  for every `ready` batch, not only the run's.
- **Run deadline and wait.**
  - The wait for a machine (queue `expiresAt`) is 5 min to 24 h, default 1 h (§3.7, A19).
  - `MAX_RUNTIME_S` = start-up allowance (20 min) + per transcribe job (audio duration × real-
    time factor 0.20 × margin 2 + overhead 60 s), `careful` jobs counted twice, capped at
    24 h. The values are placeholders recalibrated at M7. The run deadline can be shorter than
    the sum of the worker's per-job timeouts (§5.3); a run cut by it loses no finished result,
    and the next run continues.
  - Test mode: 2 h and `KEEP_POD_ALIVE=true` (above).
  - The pod name deadline (`transcribe_contracts.pods`, M3) = queue `expiresAt` +
    `MAX_RUNTIME_S` + 10 min. Constants in `runs/constants.py`.
- **Cost estimate.** Range = price per hour × (start-up 5-20 min + total transcribe-job audio
  duration × real-time factor 0.05-0.20), `careful` jobs counted twice. Price from
  `GET /v2/catalog/gpus` (read-only, secure price of `NVIDIA RTX A5000`), falling back to a
  constant (0.27 USD/h) with a note in the response. The factors are [I] and recalibrated at M7.
- **Create calls are never retried blindly.** A POST that creates something (pod, template,
  secret, global volume) is not idempotent: a retry after a lost response could start a second
  worker (§3.7 single-worker rule). 429 (after `Retry-After`) and connection errors raised
  before the request was sent are retried. After a timeout, a connection drop after sending or
  a 5xx, the client looks the object up by its name (pods: `GET /v2/pods` and
  `GET /v2/queued-pods`; the pod name carries the run id) and adopts it when found; only when
  it is not found is the POST sent again, within the attempt budget. GET and DELETE keep the
  policy of `research/runpod.md` §2 (429 `Retry-After`, 5xx backoff, other 4xx not retried).
- **The run is recorded before the pod is requested.** `launch_worker` commits the run row
  (run id, pod name, deadline, `MAX_RUNTIME_S`, covered batch ids, status `launching`) before
  the POST and stores the pod or queued-pod id after it. `refresh_status` and
  `reconcile_cloud` resolve a `launching` run by its name: found → its id is stored and the run
  follows it; in neither list while no launch call is in flight (the runs lock guarantees it,
  also after a restart) → `launch_failed`. A pod that appears later anyway is a straggler: it
  is reported by `reconcile_cloud`, and `launch_worker` refuses while it exists.
- **Cloud setup is idempotent, explicit and stateless.** `setup_cloud` creates or updates, by
  fixed names, the Runpod secrets holding the R2 credentials, the Global Volume
  (`transcribe-ui-backups`) and the template (image
  `markfazekasgh/transcribe-ui-worker:schema-<contracts major>`, `startSsh`/`startJupyter`
  false, non-secret env, secret env as `{{ RUNPOD_SECRET_<name> }}`). Template mounts can only
  be persistent volumes (`research/runpod.md` §5), so the Global Volume is not part of the
  template. Nothing about the setup is stored locally: `cloud_setup_status` looks the objects up
  by name and reports missing or outdated ones (template image tag not the app's
  `schema-<major>`), and `launch_worker` refuses with `cloud_not_set_up` or
  `cloud_setup_outdated` from the same check. Open as A18 (which R2 token the pod gets).
- **Pod create body.** `launch_worker` sends `name`, `templateId`, `gpu {id: "NVIDIA RTX
  A5000", count: 1, minCudaVersion: "12.8"}`, `cloud: SECURE`, `disk: 60`,
  `mounts.global: [{volumeId: <id of transcribe-ui-backups, looked up by name>, path:
  "/workspace"}]`, env `TRANSCRIBE_RUN_ID`/`MAX_RUNTIME_S`/`KEEP_POD_ALIVE`, and
  `queue: {expiresAt}` (§3.7).
- **Runpod keys.** The desktop's Runpod API key needs pods and queued pods read/write,
  templates, secrets and global volumes read/write (only `setup_cloud` writes these), and
  catalog read. M5.6 takes the exact scope names from the OpenAPI spec and writes them into
  §3.6. A separate pods-only terminate key for the pod (§5.2) is needed only if M4 shows that
  the pod-scoped key cannot delete its own pod. Then M5.5 adds it as an optional credential,
  `setup_cloud` stores it as a Runpod secret and the template references it (the worker reads it
  from the variable the M4 follow-up defines); until then it does not exist.
- **Secrets never leave through responses.** Runpod list and get bodies (pods carry their
  `env`) are parsed into models without `env`; no response, log line or error message contains
  env values, keys or R2 secrets.

### Other

- **R2 adapter is the desktop's own.** The worker's `pipeline/storage.py` is not shared (apps
  share only contracts); the desktop adapter follows the same boto3 settings (§6) and adds
  `head`, `copy`, `delete`, multipart abort and upload with progress.
- **ffmpeg resolution order.** The settings path override, then the bundled build
  (`sys._MEIPASS`, from M8), then `PATH` (development runs without a bundle). A `PATH` ffmpeg of
  unknown version never silently replaces the tested bundled one; `architecture.md` §3.4 says
  the same.
- **Golden files.**
  - Responses and progress events (NDJSON) are compared after normalisation: each leg's temp
    root → `<root>`, path separators → `/`, the host's path flavour value → `<flavor>`.
  - Test trees get fixed mtimes through `os.utime`; clock, local time zone, ULID randomness and
    fakes are fixed, so the normalised JSON is byte-identical on every OS.
  - Golden flows use the fake `MediaTools`. Flows with the real ffmpeg (whose output differs
    across builds and OSes) assert structure: fields, counts, codecs, durations within a
    tolerance.
  - `UPDATE_SNAPSHOTS=1` regenerates goldens and schema snapshots (the variable the contracts
    tests already use).
- **Parity runner.** Each leg gets a fresh temp root (data, config, cache and log dirs and the
  media tree), a fresh moto bucket and a fresh fake Runpod API, built by the same seeded
  factory. The backend leg calls `Backend.execute`; the CLI leg calls the CLI's `main(argv)`
  in-process with the same test wiring injected (the installed entry point runs as a subprocess
  only in M5.1's smoke test). The same sequence of requests goes through both legs, and the
  responses and progress events are compared step by step after normalisation.

## 2. Package layout

`apps/desktop/src/transcribe_ui/`, Django-like (each sub-package with `constants.py` and
`classes.py` where it has constants or Pydantic models; logic in named modules):

- `api/`: `classes.py` (the `Request`/`Response` discriminated unions, `ErrorResponse`,
  `NeedsConfirmation`, `ProgressEvent`), `errors.py` (`DomainError` with a code), `backend.py`
  (`Backend.execute`, dispatch table with the "needs database" mark), `ports.py` (`Clock`,
  `IdSource`, `ProgressSink`, `CancelToken`), `wiring.py` (composition root: real adapters for
  the CLI, fakes for tests).
- `state/`: `paths.py` (platformdirs, injectable root), `database.py` (engine, WAL, sessions,
  migrations at start-up, compare-and-set phase helper), `locks.py` (writer lock file,
  per-batch and runs locks), `models.py`, `migrations/` (`env.py`, `script.py.mako`,
  `versions/`), `settings.py`, `logs.py` (human-readable log + rotating file in the user log
  dir).
- `discovery/`: `scan.py`, `sidecars.py`, `languages.py`, `filters.py`, `selection.py`.
- `media/`: `tools.py` (ffmpeg/ffprobe resolution), `probe.py`, `convert.py`, `extract.py`,
  `fake.py`.
- `credentials/`: `store.py` (keyring + environment fallback), `services.py`.
- `storage/`: `r2.py` (`ObjectStore` protocol + boto3 adapter).
- `runpod/`: `client.py` (typed httpx v2 client), `fake.py` (fake API on `MockTransport`),
  `setup.py`.
- `batches/`: `services.py` (create/edit/delete/list/get/hide), `review.py`, `phases.py`.
- `upload/`: `services.py`, `manifest.py`.
- `runs/`: `estimate.py`, `launch.py`, `reconcile.py`, `monitor.py`.
- `placement/`: `naming.py`, `planner.py`, `custom.py`, `writer.py`.
- `cleanup/`: `services.py`, `retry.py`.
- `cli/`: `main.py` (entry point `transcribe-ui`).

Tests in `apps/desktop/tests/` (flow tests per area, `support/` helpers: parity runner, golden
files in `tests/golden/`, media generator, moto fixture, fake Runpod).

## 3. Parts

Every part is one PR that leaves `main` mergeable and green, adds its requests to the union,
its flow tests with CLI/backend parity, and moves its decisions from §1 into `architecture.md`.
"High effort" means the implementing agent runs with `effort: "high"` (concurrency or failure
handling, CLAUDE.md "Effort").

## 4. Parallelism map

- Wave 1: M5.1 alone (everything builds on the package, the façade and the parity harness).
- Wave 2, all independent new sub-packages: M5.2, M5.3, M5.4, M5.5, M5.6 (after M3 is merged),
  M5.7. Shared hot spots are one-line additions: the `Request`/`Response` unions in
  `api/classes.py`, the dispatch table in `api/backend.py`, `api/wiring.py`, `whitelist.txt`,
  `tooling.md`/`architecture.md` paragraphs; merge one at a time and rebase the rest
  (snapshots and goldens regenerated, §1). Suggested: three agents at once (M5.2, M5.4, M5.5
  first, as they are high effort and on the critical path; then M5.3, M5.6, M5.7), since every
  PR still needs a main-session review.
- Wave 3: M5.8 (needs M5.2, M5.3, M5.4).
- Wave 4: M5.9 and M5.10 in parallel (both need M5.8; M5.9 also M5.5, M5.10 also M5.5 and
  M5.6); M5.11 follows M5.10 while M5.9 may still be open.
- Wave 5: M5.12 (needs M5.7, M5.9, M5.11); M5.13's retry and cleanup are written alongside
  and merged after M5.12.

Critical path: M5.1 → M5.2 → M5.8 → M5.10 → M5.11 → M5.12 → M5.13 (M5.9 runs alongside
M5.10-M5.11).

## 5. Risks

- Windows CI leg: ffmpeg availability and path/locking differences (`os.replace` onto an open
  file, SQLite file locks). Found early by M5.1/M5.2 on `windows-2025`.
- moto does not reproduce R2's checksum behaviour (research/desktop-packaging.md §4); an
  `integration`-marked R2 test with the real bucket runs locally before M7.
- Runpod v2 details the fake encodes (queue 202 body, secret syntax in templates, catalog
  shape, list endpoints for secrets and global volumes, key scope names) are from the OpenAPI
  spec, not from a real call; M4/M7 verify them, the fake is updated then.
- Cost and runtime constants are guesses until M7 measures a real run.
