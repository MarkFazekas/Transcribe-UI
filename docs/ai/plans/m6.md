# M6 plan: desktop frontends

Milestone M6 of `architecture.md` §10: a PySide6 GUI and a more usable CLI over the M5 backend
façade, both sending the same `Request` models (§3.1). It serves `docs/human/requirements.md`
sections "UI app: file selection", "UI app: review step", "Subtitle download options", "Cloud
cleanup", "Runpod control", "Failure handling" (desktop side) and "Architecture and code quality"
(frontends hold no business logic; the same request gives the same response from every
frontend; this is testable). The design is `architecture.md` §3.1 (boundary), §3.2-§3.8 (the
requests), §7 (tests) and §8 (CI). Packaging is M8; this plan only keeps the GUI ready for the
one-file builds (two executables per platform, A20). Real Runpod runs are M7.

The GUI toolkit is fixed by the requirements ("Desktop stack *(accepted proposal)*: PySide6,
PyInstaller one-file, static LGPL ffmpeg bundled, unsigned builds for four platforms"; research in
`research/desktop-packaging.md` §1), so it is not an open question.

Open questions the plan is written on (their proposed defaults): Q35
(`questions-for-product.md`), and A21 and A22 (`questions-for-architect.md`) for
M6.13. Answered: Q28 (its default, extended to several installations on one bucket,
architecture §3.9), Q29, Q30 and Q31 (their defaults; Q30 in §1 "Closing the window", Q31 in §1
"Long requests"), Q32 (Hungarian and English catalogs, §1 "Texts", M6.14), Q33 (A+C, §1
"Layout") and Q34 (its default: Cancel and Stop, both confirmed). An answer that differs changes the part that implements it.

## 1. Decisions taken for M6

Conventional defaults where the docs leave a gap. The part that implements a decision writes it
into `architecture.md` (§3.1 for the frontends) or `tooling.md`; this plan changes afterwards
only by the **(built)** markers.

### Frontend rules

- **No business logic in a frontend.** A frontend turns user input into a `Request`, sends it,
  and renders the `Response` and the `ProgressEvent`s. Whether an action is allowed, what a
  confirmation means, how a selection or a filter resolves, what a phase or a status implies:
  all of it comes from the backend's responses. Where the GUI would otherwise have to re-derive
  a rule, the backend reports it (M6.1: the batch's allowed actions, the confirmation's value,
  the stored composition, the run list, the current file's name). Pure presentation stays in the
  GUI: labels, sorting a table the user clicked, formatting durations and money, which page is
  visible.
- **Qt-free view-models.** Each GUI area has a view-model in plain Python (no Qt import): it
  holds the widget state as data, builds the requests (`build_*_request()`), sends them through
  an injected `Executor` port and turns responses into display data. Qt widgets only bind to
  the view-model. So most GUI tests run without a display, and the request a widget state
  produces is checked directly (§1 "Testing").
- **Same request, same response.** The GUI sends requests through `Backend.execute` with the
  same models and the same ports as the CLI; the bridge (below) does not transform requests,
  responses or progress events. The parity runner gets a GUI leg that proves it (M6.2).
- **Settings only pre-fill.** The GUI reads `get_settings` at start-up and after a save, and
  fills machine-dependent request fields from it (scan extensions and `include_hidden`, placement
  defaults, enabled languages in choosers). The backend never reads settings for a request
  (§3.8); a request the GUI sends is complete on its own and could be replayed by the CLI.
- **Confirmations are data, always.** A `needs_confirmation` response is shown by one dialog for
  every action: each `Confirmation`'s message and its details (a table where the details hold a
  list, such as overwritten targets or the launch plan). Accepting re-sends the same request
  with each `field` set to the confirmation's `set_to` value (M6.1). The launch confirmation
  (`confirm_fingerprint`) has its own richer dialog (plan, wait for a machine, test mode), which
  still only copies `set_to`. Destructive requests that had no confirmation get one in the
  backend (M6.1: `delete_batch`, `exclude_items`), so every frontend applies the same rule and the
  GUI has no confirmation of its own for a request. The only GUI-side question is closing the
  window with work in flight (Q30), which sends no request.

### Backend additions for the frontends (M6.1)

- **`Confirmation.set_to`** (`JsonValue`): the value that confirms the field; `true` for the
  boolean fields (`confirm`, `confirm_existing_languages`, `confirm_not_downloaded`,
  `confirm_overwrite`), the plan's fingerprint for `confirm_fingerprint`. Every frontend
  (GUI, CLI user, later MCP) confirms the same way. Named `set_to`, not `value` (WPS110).
- **Confirmations for `delete_batch` and `exclude_items`**: a `confirm` field (default false);
  without it the request answers `needs_confirmation` (the batch, the number of items and, for
  `exclude_items` in `uploading`, that their uploaded audio is deleted) and changes nothing.
  Existing flows and goldens that delete or exclude send `confirm: true` or gain the asking
  step (regenerated).
- **Allowed actions per batch.** `BatchSummary.actions`: the batch requests whose local
  preconditions hold now (phase, flags, item and job states, `cleanup_pending`), computed from
  one table in `batches/actions.py`. The handlers' existing guards are not rewritten; a
  table-driven drift test links the two (every listed action passes its handler's local guard,
  every unlisted one is refused by it), so they cannot diverge silently. Cloud-side and lock
  conditions (run active, busy, cloud unreachable) are not in the table: a listed action can
  still be refused, and the GUI shows that error.
- **Stored composition.** Today the batch payload keeps only `scan_root`, `path_flavor` and the
  languages (`batches/payloads.py` `BatchPayload`), so "Edit selection" could not reopen the
  selection. `create_batch` and `edit_batch` store their composition (the `ScanSpec`, the
  operations, `languages`, `item_languages`) in the payload, and `BatchDetail.composition`
  returns it (None for a batch created before, or a retry batch). This is a change of a stored
  payload's shape, so it is a new Alembic revision that rewrites stored payloads with
  `composition: null` (architecture §3.8; `status.md` "Next").
- **Stored run report.** `RunPayload` keeps no worker report, and `RunProgress` built without
  one reads as "starting". `refresh_status` stores, at each refresh of a run, the last worker
  report (`WorkerProgress`), the `stop_error` and the refresh time (`refreshed_at`) in the run
  payload; again a payload shape change with its own revision (existing rows: none stored).
- **`list_runs`** (database only, no Runpod or R2 call; field `limit`, default 20): the latest
  runs, newest first, as `RunProgress` from the stored values only. It never measures against
  now: elapsed time and cost run to `ended_at`, else to `refreshed_at` (as of the last refresh),
  and the response says so per run. The cloud page shows the last run's outcome, end reason,
  worker report and kept worker log after a restart, which `refresh_status` (non-final runs
  only) cannot.
- **`CurrentJob.name`**: the file name of the job the worker reports (None for a batch this
  database does not know), so "which job and file" (requirements "Runpod control") needs no
  lookup in the GUI.
- Not needed: the subtitles a file already has are in the scan response
  (`ScanFile.subtitles`: language and forced flag per sidecar) and in `preview_selection`'s
  selected files, so the tree can show them without a backend change.

### GUI architecture

- **Package.** `transcribe_ui/gui/`: `app.py` (start-up, `run_gui`), `bridge.py` (the Qt
  executor), `executor.py` (the `Executor` protocol, call handles and channels; Qt-free),
  `feedback.py` (error and confirmation view data; Qt-free), `dialogs.py` (their Qt dialogs),
  `activity.py` (the window-level panel of long calls: progress, Cancel, Resume), `signals.py`
  (the navigation and action bus, below), `shell.py` (main window, navigation, wiring of the
  bus), `display.py` (the display check),
  `main.py` (the GUI entry, `transcribe_ui.gui.main:run`), `constants.py`; one sub-package per area, each owned by one part: `settings/`, `selection/`,
  `jobs/`, `review/`, `cloud/`, `download/`, `cleanup/`, each with `viewmodel.py` (Qt-free) and
  `view.py` (widgets), `models.py` only where a Qt item model is needed (the selection tree).
- **Cross-area contract, declared up front.** M6.2 writes `gui/signals.py` with every
  cross-area signal before any area exists, so later parts connect to it instead of editing each
  other's packages:
  - navigation: `open_job(batch_id)`, `open_jobs()`, `open_new_job()`, `open_cloud()`,
    `open_cloud_machines()`, `open_settings(section)`;
  - job actions, emitted by the job page: `edit_selection(batch_id)` (handled by
    `selection/`), `open_review(batch_id)` and `run_upload(batch_id)` (`review/`),
    `open_download(batch_id)` (`download/`), `retry_jobs(batch_id, jobs)` and
    `clean_up(batch_id, scope)` (`cleanup/`);
  - cloud actions, emitted by the start dialog: `delete_unknown_batch(batch_id)` (`cleanup/`),
    and `plan_invalidated()` back to the start dialog after such a delete;
  - changes: `batches_changed(batch_ids)`, `runs_changed()`, `settings_changed()`;
  - start-up hooks: an ordered list of start-up steps that areas register into (the sequence
    below), run by `app.py`.

  The job page (M6.5) builds every job button from `actions` and only emits the signal; the
  start dialog (M6.6) builds the unknown-batch "Delete from cloud" button and only emits. So no
  later part edits `gui/jobs/` or `gui/cloud/`: M6.8-M6.10 add their handlers in their own
  package and one connection line each in `gui/shell.py`. A part that still needs a change in
  another area's package lands it as a small separate PR first, not inside the part.
- **Dependencies.** `pyside6-essentials` (QtCore, QtGui, QtWidgets, QtTest; LGPL modules only,
  smaller than the full `pyside6`) as a runtime dependency and `pytest-qt` as a dev dependency,
  both added by M6.2, so later parts do not touch `uv.lock`. No other new dependency in M6.
- **Entry points** (two executables per platform, A20). The CLI entry `transcribe-ui`
  (`transcribe_ui.cli.main:run`, a console program) serves `run`, `schema`, `--version` and
  (from M6.7) `credentials`; it has no `gui` command and never imports Qt, directly or
  through the modules it imports. The GUI entry `transcribe-ui-gui`
  (`transcribe_ui.gui.main:run`, a GUI-script, windowed on Windows) takes no arguments and
  opens the GUI. Both build the backend the same way. The display check accepts `QT_QPA_PLATFORM=offscreen`
  as a display, so M8's GUI smoke run can start and quit the GUI on a headless runner. M8 builds one PyInstaller executable
  from each entry; the app does not handle the Windows console itself.
  - Before importing Qt, `gui/display.py` checks for a display: on Linux and other non-macOS
    POSIX systems at least one of `DISPLAY` and `WAYLAND_DISPLAY` must be set (Qt's own failure
    to load a platform plugin aborts the process, which cannot be answered). Without one, the
    GUI entry answers like the CLI: a JSON `ErrorResponse` on stdout with the new code
    `display_unavailable` (message: use the CLI executable with `run <request.json>`) and exit code 1.
  - Qt's own messages (warnings, platform plugin notes) go to the GUI log through
    `qInstallMessageHandler`, never to stderr. The GUI logs to `transcribe-ui-gui.log` (§3.8).
  - The GUI builds its backend with `build_backend()`; `run_gui(make_backend=...)` takes a
    factory, so tests inject `seeded_ports`.
- **Threading.** The backend's calls block (scans, ffmpeg, R2, Runpod, the runs lock's bounded
  wait of 30 s), so the GUI thread never calls `Backend.execute`.
  - `bridge.QtExecutor` runs each request as a `QRunnable`. The runnable calls
    `Backend.execute` with a `CancelFlag` and a progress sink; the sink and the completion emit
    signals of a `QObject` that lives in the GUI thread (queued connections), so widgets are only
    touched on the GUI thread. The bridge passes every event on in order, unchanged; views
    throttle their repaint (`PROGRESS_REPAINT_MS` = 100) instead.
  - **Three pools**, so short requests never wait behind long ones. A table in
    `gui/constants.py` maps each action to its pool (presentation of threading, not a business
    rule):
    - `long` (`LONG_POOL_THREADS` = 3): `scan_tree`, `review_batch`, `run_upload`,
      `run_download`, `import_custom_plan`, `create_retry_batch`, `cleanup_cloud`,
      `setup_cloud`;
    - `short` (`SHORT_POOL_THREADS` = 3): every other user-started request, including
      `preview_selection`, the `get_*`/`list_*` and status requests, `plan_launch`,
      `launch_worker`, and the stops (`cancel_worker`, `terminate_pod`, `cancel_queued_pod`),
      so Stop is never queued behind an upload;
    - `poll` (one reserved thread): `refresh_status` and `reconcile_cloud`, from the start-up
      sequence, the poll and Refresh now.
  - A call returns a handle (`cancel()`, `state`: `queued`, `running` or `done`). Cancelling:
    - a queued call is taken off its pool with `QThreadPool.tryTake`; when that succeeds the
      handle completes at once with the `cancelled` error (the same `ErrorResponse` the backend
      gives), and the request never runs;
    - the runnable checks its cancel flag before calling `execute` (a call cancelled between
      being dequeued and starting) and completes with `cancelled` without running the request;
    - a running call gets its flag set; the backend stops between steps (§3.1).
  - A **channel** names what may run at once:
    - `exclusive`: one call per key; a second send while one is queued or running is refused
      in the view-model (one `run_upload` per batch);
    - `latest`: a new send cancels the previous call of the key (taken off the pool if still
      queued) and its stale response is dropped by sequence number (`preview_selection` on
      every click, `review_batch` on a filter change);
    - `single_flight`: the poll. The channel tracks the handle's `state`, not a "busy" flag: a
      new tick is not sent while the previous tick is `queued` or `running` (no duplicates pile
      up), the page shows "refreshing" only while it is `running` (a queued tick shows "waiting
      to refresh"), and a queued tick that is cancelled or taken off its pool releases the
      channel at once, so a starved tick can never block the poll for good. The reserved poll
      thread keeps ticks from queueing behind anything but a start-up check or Refresh now.
    The backend still guards everything with its locks (§3.8); channels and pools only keep the
    GUI from producing avoidable `batch_busy`/`runs_busy` errors and waits.
  - `executor.SyncExecutor` runs calls inline for view-model tests (deterministic, no Qt).
- **Writer lock.** The GUI's backend takes the writer lock with its first database request
  (§3.8) and keeps it until the window closes. If another process holds it (`app_busy`: a CLI
  run or a second GUI), the window shows a blocking notice with Retry instead of the pages that
  need the database; settings, credentials and cloud setup stay usable (they need no database).
- **Start-up sequence** (background, after the window shows): `get_settings`,
  `credentials_status`, `list_batches`, `list_runs`; then `reconcile_cloud` when a Runpod key
  is set (reconcile resolves `launching` runs, and refresh never calls reconcile), followed by
  `refresh_status` (until M6.13, only when a Runpod key is set; from M6.13 also without one,
  architecture §3.9). Missing credentials show a first-run notice linking to the
  settings page; a cloud error (`cloud_unreachable`, `credentials_invalid`, ...) shows a
  non-blocking banner with Retry. `reconcile_cloud`'s `attention` shows a banner linking to the
  cloud machines list (stragglers, overdue pods).
- **Refresh while a run is active.** While the last `refresh_status`, `launch_worker` or
  `list_runs` response holds a run that is not final, the cloud page polls `refresh_status`
  every `REFRESH_INTERVAL_S` (300 s, in `gui/constants.py`; requirements "Runpod control") on the `poll` pool and a `single_flight` channel, plus a
  "Refresh now" button. Polling stops after a refresh whose runs are all final. A poll's
  `runs_busy`, `state_busy` or `cloud_unreachable` is shown as "last updated <time>, retrying"
  and retried at the next tick, not as an error dialog. Elapsed time and cost are shown as of the
  last refresh ("updated hh:mm:ss"); the GUI does not extrapolate them. The remaining time is the exception in display only: a
  countdown each second to the backend's `estimated_finish_at` (replaced at each refresh; at 0
  before the run is final it shows "finishing", never negative), next to a progress bar from
  `progress_fraction` on the cloud and job pages; the GUI computes neither (M6.12). The 5-minute poll
  keeps the desktop deadline stop working: it comes at most 300 s late, inside the 10 min
  `DESKTOP_DEADLINE_MARGIN_S`, and the reaper is the backstop. When a run ends, the
  window flashes in the task bar (`QApplication.alert`) and `runs_changed` and
  `batches_changed` reload the pages.
- **Long requests** (the `long` pool): the activity panel shows each call's current stage,
  `completed`/`total` and the path of the event, with a Cancel button that sets the call's
  cancel flag. The `cancelled` error is shown as a neutral "Stopped; continue any time" with a
  Resume button that re-sends the same request (§3.1: re-sending resumes), never as a failure.
  Interrupted work is shown from the batch's phase and flags after a restart (Q31, answered:
  the default). No step starts on its own: Upload, Start transcription, Download and Resume
  are each one button. The only automatic requests are checks: `reconcile_cloud` and
  `refresh_status` at start-up, and the poll while a run is not final or, from M6.13, while the
  response's `awaiting_results` says so (architecture §3.9). The jobs
  list marks interrupted jobs and jobs with subtitles ready (M6.5).
- **Closing the window** (Q30, answered: the default): with calls queued or running, the user
  confirms ("Stop and close? The work continues from where it stopped the next time you start
  it."). The GUI then
  calls `clear()` on every pool (queued calls never start; their handles complete as
  `cancelled`), sets the flag of every running call, and waits for them in a modal "Finishing
  the current step" dialog. Its "Quit now" button flushes and closes the log handlers, then
  ends the process with `os._exit` (not `sys.exit`, which would wait for the pool threads);
  like the CLI's second Ctrl+C this loses nothing, since every step is idempotent. With a run
  that is not final, the close dialog says that the cloud machine keeps working without the
  app, stops itself when the work is done or at its time limit (worker watchdog and the reaper,
  §5.2), and that the app shows its results at the next start. Closing never cancels the run;
  Cancel and Stop are on the Cloud page (Q34). On a normal close the backend's `ports.state` is closed last.
- **Errors.** An `ErrorResponse` is shown where the action was started (a banner in the page,
  or a dialog for a modal action): the message, then a collapsed "Details" section with the
  code, the details as a table, and "Open log folder". A small table maps codes that have a
  fix in the GUI to a button (`credentials_missing`/`credentials_invalid` → settings page,
  `cloud_not_set_up`/`cloud_setup_outdated` → cloud setup, `cleanup_pending` → the batch named
  in the details, `app_busy` → Retry); that table is presentation, the decision stays the
  backend's. `internal_error` adds "see the log". Unknown codes render with the generic layout,
  so a new backend code never breaks the GUI.
- **Texts** (Q32): every user-visible string of an area lives in its view-model or `view.py`,
  marked with `tr()`/`ntr()`, and the part that adds it also adds its Hungarian translation
  (the catalog check fails otherwise). Errors are shown from the catalog entry of their code
  (architecture §3.1 "Language of the texts"), not from the backend's `message`.
- **Layout** (Q33, answered "A+C": the frame of A with the guided steps of C inside it):
  - Frame (A): a main window with a left navigation of four pages: "New job" (folder tree,
    filters, selection, languages), "Jobs" (history list and the job page with review,
    upload, download, retry and cleanup), "Cloud" (start transcription, the current and last
    runs, cloud machines), "Settings" (languages, file types, ffmpeg, placement defaults,
    accounts, cloud setup, about); and an always-visible status bar at the bottom: the cloud
    run (stage, countdown) and the jobs with a long step running (converting, uploading,
    downloading), each a link back to its job.
  - Steps (C): a job is shown with a step header: 1 Files (folder, tree, filters, languages)
    → 2 Review & upload → 3 Start transcription (the cost and time estimate and the jobs ready)
    → 4 Download, with Back and Next. New job starts at step 1; the user can leave at any step
    (the work continues and the job is on Jobs). Opening a job from Jobs shows the same header
    at its current step, with that step's action.
  - The step comes from the backend: `BatchSummary.stage` (`files`, `review_upload`,
    `transcription`, `download`, `done`), derived from the phase and flags in the same table as
    `actions` (`batches/actions.py`); the GUI only renders it. Which buttons a step shows still
    comes from `actions`.
  - Work in parallel: while a job converts or uploads (`run_upload` on the `long` pool), New job
    can be started again: a fresh step 1, whose scan and selection run alongside. The `long`
    pool's 3 threads allow this; a fourth long call waits and is shown as waiting in the
    activity panel.
  - First start: while an R2 credential is missing (`credentials_status`), or a Runpod key is
    set and the cloud setup is not complete (`cloud_setup_status`), the app opens a short
    set-up wizard (accounts, then cloud setup when a Runpod key was entered) before New job.
    It can be closed; Settings has the same pages.

### CLI

- **Still JSON first.** `transcribe-ui run <request.json>` stays the CLI for every request
  (requirements: the surface is too complex for flags); every request action has its GUI page
  and is reachable from the CLI only through `run`. M6 adds ergonomics, no new semantics:
  - `run -` reads the request from stdin (same UTF-8 rules), so a script or an LLM can pipe it.
    Windows PowerShell 5.1 pipes text to a native program in `$OutputEncoding`, ASCII by
    default, which turns non-ASCII paths into `?`: §3.1 documents setting
    `$OutputEncoding = [System.Text.UTF8Encoding]::new($false)` first, and recommends the file
    form there (PowerShell 7 pipes UTF-8).
  - `run --progress text` writes one human-readable line per event to stderr instead of NDJSON
    (default stays `ndjson`, so scripts keep working).
  - `credentials` (new in M6.7): prompts for each credential without echo (`getpass`; Enter
    skips a field), builds a `StoreCredentialsRequest` and prints its response like `run`, so
    secrets never sit in a file or in shell history. Refused with `invalid_arguments` when
    stdin is not a terminal (use a request file there).
  - Confirming from the CLI: the `needs_confirmation` response names each `field` and its
    `set_to`; the user adds them to the request file and runs it again (documented in §3.1).
  - The GUI is the separate GUI entry (A20); the CLI has no `gui` command.

### Testing

- **View-model tests** (most GUI tests; no display needed): a view-model on `SyncExecutor`
  over a seeded backend (`support.fakes.seeded_ports`, moto, the fake Runpod API), driven like
  a user (set filters, tick folders, confirm), asserting the requests it builds and the display
  data it derives.
- **Request goldens.** The request a view-model builds for a scripted widget state is written as
  JSON to `apps/desktop/tests/golden/gui_<area>_*.json` and compared byte for byte (normalised
  like responses, §7). The same documents then run through the parity runner's backend and CLI
  legs, so a GUI-built request is proven to be a valid CLI request with the same response.
- **Bridge parity.** A third parity leg, `gui`, in its own module
  (`tests/support/gui_parity.py`, reusing the leg factory of `support/parity.py` unchanged): the
  request goes through `QtExecutor` on its pools (pytest-qt `qtbot.waitSignal`), and the
  response, progress events and their order must equal the backend leg's. Run for one request
  of every area.
- **Widget smoke tests** (pytest-qt): each page builds, binds to its view-model, a few clicks
  reach the expected request; the selection tree model passes `QAbstractItemModelTester`; the
  close-with-calls-in-flight path, cancel and resume, the `app_busy` notice and the start-up
  sequence are exercised with a scripted executor. No screenshot or pixel comparison (fonts and
  styles differ by OS).
- **CI.** The GUI tests run in the desktop target on `ubuntu-24.04` and `windows-2025` with
  `QT_QPA_PLATFORM=offscreen` (set in `conftest.py` with `setdefault`, so a developer can
  override it to see the windows); no Xvfb. The Ubuntu leg installs the libraries Qt loads even
  offscreen (M6.2 settles the minimal apt list, expected `libegl1`, `libgl1`, `libxkbcommon0`,
  `libfontconfig1`, `libdbus-1-3`). macOS gets the GUI first in M8's build smoke run.
- **Lint.** Qt item-model and event overrides must keep Qt's names (`rowCount`, `data`,
  `index`, `paintEvent`, ...). Every such method carries `@typing.override` (mypy then checks
  that it really overrides), which ruff's N802 honours. M6.2 checks whether flake8's pep8-naming
  honours it too; where a linter does not (pep8-naming N802, WPS110 for Qt API names such as
  `data` and `index`), matching per-file-ignores limited to those codes go into both `.flake8`
  and ruff's config for `gui/**/models.py` and `gui/**/view.py`, with a comment. Everything else
  is fixed, not suppressed. mypy strict uses PySide6's own stubs; an override is added only for a
  stub gap found in practice, with the reason. Spellcheck words (`qt`, `pyside`, ...) are added
  to `whitelist.txt` by the part that first needs them.

## 2. Request coverage

Every request action of `api/classes.py` and where the GUI uses it. Every action is also a CLI
request through `transcribe-ui run <request.json>` (or `run -`); only the extra CLI entry points
M6 adds are named below.

- Settings and accounts (M6.3):
  - `get_app_info`: Settings → About; the window title's version.
  - `get_settings`: start-up; Settings pages.
  - `update_settings`: Settings → Save (the whole document; `invalid_request` details shown per
    field).
  - `store_credentials`: Settings → Accounts → Save (only the fields the user changed). CLI:
    also `transcribe-ui credentials` (M6.7).
  - `credentials_status`: start-up (first-run notice); Accounts page (set / from environment /
    missing, never values).
  - `check_credentials`: Accounts → Test.
  - `cloud_setup_status`: Settings → Cloud setup (missing, outdated, duplicated objects; Q29: the
    error's volume ids listed, no other UI for it).
  - `setup_cloud`: Cloud setup → Set up / Update (long request with progress).
- New job (M6.4):
  - `scan_tree`: New job → Choose folder (scan options from the settings; warnings listed).
  - `preview_selection`: every tick, untick and filter change (`latest` channel, the scan's
    `scan_id` passed); the tree's tri-state and the totals come from its response.

## 5. Risks

- **Qt leaking into the CLI entry** (A20: two executables, the CLI one without Qt): one
  import of `PySide6` (or of a `gui` module) anywhere in the CLI's whole import graph (`cli`,
  `api` and every backend package) would break the CLI build or bloat it. M6.2's test guards
  it; later parts keep that whole graph free of `gui` imports. M8's CLI build excludes
  PySide6, so such an import fails its `--version` smoke run too; the GUI build is smoke-tested
  with an offscreen start and quit.
- **Qt on CI**: the offscreen platform still loads EGL/GL, xkbcommon and fontconfig on Linux;
  Windows offscreen has fewer gaps. M6.2 settles the apt list early; a missing library fails
  every GUI test at import, not silently.
- **Thread safety of the ports** under concurrent GUI calls: the backend is documented
  thread-safe (§3.8, the scan cache is locked), but no M5 test ran a scan, a refresh and an
  upload at the same time. M6.2's bridge tests run mixed requests in parallel on the seeded
  backend.
- **Shutdown and lock waits**: a call can sit in the runs lock's 30 s wait or in Runpod retries
  when the user closes the window. "Quit now" is the escape; every step is idempotent, so a
  forced exit loses no state (as with the CLI's second Ctrl+C).
- **Preview latency on large trees**: `preview_selection` runs the filters over every file of
  the cached scan on each click. Latest-wins cancellation keeps the GUI responsive; if a 20 000
  file tree is still slow, the backend's preview gets faster (a backend change in M6.4), not a
  GUI-side shortcut.
- **mypy strict and WPS with PySide6**: signal typing and Qt override names cause friction;
  `@override` plus limited per-file ignores (§1 "Lint") are the budget, anything beyond goes to
  the architect.
- **Backend API and stored data**: M6.1 changes response shapes (`actions`, `set_to`,
  `composition`, `name`), two request types (`confirm`) and stored payloads (a revision). Done
  once, before the GUI parts, so later parts do not regenerate shared goldens; the revision is
  tested on a database with old payloads.
- **Polling cost**: one `refresh_status` every 300 s reads two Runpod lists; a 24 h wait for a
  machine is about 580 list calls. Runpod's rate limits are not documented in
  `research/runpod.md`; the client honours 429 `Retry-After` and the single-flight poll never
  piles calls up. M7 observes it on a real run.
