# M6 plan: desktop frontends

Milestone M6 of `architecture.md` §10: a PySide6 GUI and a more usable CLI over the M5 backend
façade, both sending the same `Request` models (§3.1). It serves `docs/human/requirements.md`
sections "UI app: file selection", "UI app: review step", "Subtitle download options", "Cloud
cleanup", "Runpod control", "Failure handling" (desktop side) and "Architecture and code quality"
(frontends hold no business logic; the same request gives the same response from every
frontend; this is testable). The design is `architecture.md` §3.1 (boundary), §3.2-§3.8 (the
requests), §7 (tests) and §8 (CI). Packaging is M8; this plan only keeps the GUI ready for the
one-file builds. Real Runpod runs are M7.

The GUI toolkit is fixed by the requirements ("Desktop stack *(accepted proposal)*: PySide6,
PyInstaller one-file, static LGPL ffmpeg bundled, four unsigned builds"; research in
`research/desktop-packaging.md` §1), so it is not an open question.

Open questions the plan is written on (their proposed defaults): A20
(`questions-for-architect.md`); Q30-Q34 (`questions-for-product.md`); Q22-Q29 as in M5. An answer
that differs changes the part that implements it.

## 1. Decisions taken for M6

Conventional defaults where the docs leave a gap. The part that implements a decision writes it
into `architecture.md` (§3.1 for the frontends) or `tooling.md`; this plan changes afterwards
only by the **(built)** markers.

### Frontend rules

- **No business logic in a frontend.** A frontend turns user input into a `Request`, sends it,
  and renders the `Response` and the `ProgressEvent`s. Whether an action is allowed, what a
  confirmation means, how a selection or a filter resolves, what a phase or a status implies:
  all of it comes from the backend's responses. Where the GUI would otherwise have to re-derive
  a rule, the backend reports it (M6.1: the batch's allowed actions, the confirmation's value,
  the run list, the current file's name). Pure presentation stays in the GUI: labels, sorting a
  table the user clicked, formatting durations and money, which page is visible.
- **Qt-free view-models.** Each GUI area has a view-model in plain Python (no Qt import): it
  holds the widget state as data, builds the requests (`build_*_request()`), sends them through
  an injected `Executor` port and turns responses into display data. Qt widgets only bind to
  the view-model. So most GUI tests run without a display, and the request a widget state
  produces is checked directly (§1 "Testing").
- **Same request, same response.** The GUI sends requests through `Backend.execute` with the
  same models and the same ports as the CLI; the bridge (below) does not transform requests,
  responses or progress events. The parity runner gets a GUI leg that proves it (M6.2).
- **Settings only pre-fill.** The GUI reads `get_settings` at start-up and after a save, and
  fills machine-dependent request fields from it (scan extensions and `include_hidden`, placement
  defaults, enabled languages in choosers). The backend never reads settings for a request
  (§3.8); a request the GUI sends is complete on its own and could be replayed by the CLI.
- **Confirmations are generic.** A `needs_confirmation` response is shown by one dialog for
  every action: each `Confirmation`'s message and its details (a table where the details hold a
  list, such as overwritten targets or the launch plan). Accepting re-sends the same request
  with each `field` set to the confirmation's `set_to` value (M6.1). The launch confirmation
  (`confirm_fingerprint`) has its own richer dialog (plan, wait for a machine, test mode), which
  still only copies `set_to`. GUI-only "Are you sure?" questions exist only for destructive
  steps the backend does not confirm (`delete_batch` of a composing or reviewing batch,
  `exclude_items`, closing the app with work in flight, Q30).

### Backend additions for the frontends (M6.1)

- **`Confirmation.set_to`** (`JsonValue`): the value that confirms the field; `true` for the
  boolean fields (`confirm`, `confirm_existing_languages`, `confirm_not_downloaded`,
  `confirm_overwrite`), the plan's fingerprint for `confirm_fingerprint`. Every frontend
  (GUI, CLI user, later MCP) confirms the same way. Named `set_to`, not `value` (WPS110).
- **Allowed actions per batch.** `BatchSummary.actions`: the batch requests whose local
  preconditions hold now (phase, flags, item and job states, `cleanup_pending`), from one table
  in `batches/actions.py` that the handlers' own phase guards use too, so the list and the
  guards cannot drift. Cloud-side and lock conditions (run active, busy, cloud unreachable) are
  not in it: a listed action can still be refused, and the GUI shows that error.
- **`list_runs`** (database only, no Runpod or R2 call; field `limit`, default 20): the latest
  runs, newest first, as `RunProgress` with the values of the last refresh. The cloud page shows
  the last run's outcome, end reason and kept worker log after a restart, which
  `refresh_status` (non-final runs only) cannot.
- **`CurrentJob.name`**: the file name of the job the worker reports (None for a batch this
  database does not know), so "which job and file" (requirements "Runpod control") needs no
  lookup in the GUI.

### GUI architecture

- **Package.** `transcribe_ui/gui/`: `app.py` (start-up, `run_gui`), `bridge.py` (the Qt
  executor), `executor.py` (the `Executor` protocol, call handles and channels; Qt-free),
  `feedback.py` (error and confirmation view data; Qt-free), `dialogs.py` (their Qt dialogs),
  `shell.py` (main window and navigation), `console.py` (Windows console handling, A20),
  `constants.py`; one sub-package per area, each owned by one part: `settings/`, `selection/`,
  `jobs/`, `review/`, `cloud/`, `download/`, `cleanup/`, each with `viewmodel.py` (Qt-free) and
  `view.py` (widgets), `models.py` only where a Qt item model is needed (the selection tree).
  Per-area sub-packages keep parallel parts in disjoint files.
- **Dependencies.** `pyside6-essentials` (QtCore, QtGui, QtWidgets, QtTest; LGPL modules only,
  smaller than the full `pyside6`) as a runtime dependency and `pytest-qt` as a dev dependency,
  both added by M6.2, so later parts do not touch `uv.lock`. No other new dependency in M6.
- **Entry point.** One `transcribe-ui` executable (A20): no arguments, or the `gui` command,
  starts the GUI; `run`, `schema`, `credentials` and `--version` stay CLI commands. `cli/main.py`
  imports the GUI lazily (`importlib.import_module`), so a CLI run never loads Qt. The GUI
  logs to `transcribe-ui-gui.log` (§3.8) and builds its backend with `build_backend()`;
  `run_gui(make_backend=...)` takes a factory, so tests inject `seeded_ports`.
- **Threading.** The backend's calls block (scans, ffmpeg, R2, Runpod, the runs lock's bounded
  wait of 30 s), so the GUI thread never calls `Backend.execute`.
  - `bridge.QtExecutor` runs each request as a `QRunnable` on its own `QThreadPool`
    (`GUI_WORKER_THREADS` = 4). The runnable calls `Backend.execute` with a `CancelFlag` and a
    progress sink; the sink and the completion emit signals of a `QObject` that lives in the GUI
    thread (queued connections), so widgets are only touched on the GUI thread. The bridge
    passes every event on in order, unchanged; views throttle their repaint
    (`PROGRESS_REPAINT_MS` = 100) instead.
  - A call returns a handle (`cancel()`, `done`). A **channel** names what may run at once:
    `exclusive` (one call per key; a second send while one runs is refused in the view-model,
    e.g. one `run_upload` per batch), `latest` (a new send cancels the previous call of the key
    and its stale response is dropped by sequence number: `preview_selection` on every click,
    `review_batch` on a filter change), `single_flight` (a send while one runs is skipped: the
    refresh poll). The backend still guards everything with its locks (§3.8); channels only
    keep the GUI from producing avoidable `batch_busy`/`runs_busy` errors.
  - `executor.SyncExecutor` runs calls inline for view-model tests (deterministic, no Qt).
- **Writer lock.** The GUI's backend takes the writer lock with its first database request
  (§3.8) and keeps it until the window closes. If another process holds it (`app_busy`: a CLI
  run or a second GUI), the window shows a blocking notice with Retry instead of the pages that
  need the database; settings, credentials and cloud setup stay usable (they need no database).
- **Start-up sequence** (background, after the window shows): `get_settings`,
  `credentials_status`, `list_batches`, `list_runs`; then, only when a Runpod key is set,
  `reconcile_cloud` followed by `refresh_status` (reconcile resolves `launching` runs, and
  refresh never calls reconcile). Missing credentials show a first-run notice linking to the
  settings page; a cloud error (`cloud_unreachable`, `credentials_invalid`, ...) shows a
  non-blocking banner with Retry. `reconcile_cloud`'s `attention` shows a banner linking to the
  cloud machines list (stragglers, overdue pods).
- **Refresh while a run is active.** While the last `refresh_status`, `launch_worker` or
  `list_runs` response holds a run that is not final, the cloud page polls `refresh_status`
  every `REFRESH_INTERVAL_S` (30 s) on a `single_flight` channel (a tick is skipped while one
  runs), plus a "Refresh now" button. Polling stops after a refresh whose runs are all final.
  A poll's `runs_busy`, `state_busy` or `cloud_unreachable` is shown as "last updated <time>,
  retrying" and retried at the next tick, not as an error dialog. Elapsed time and cost are
  shown as of the last refresh ("updated hh:mm:ss"); the GUI does not extrapolate them. When a
  run ends, the window flashes in the task bar (`QApplication.alert`) and the jobs list reloads.
- **Long requests** (`scan_tree`, `review_batch`, `run_upload`, `run_download`,
  `import_custom_plan`, `create_retry_batch`, `cleanup_cloud`, `setup_cloud`): a progress panel
  in the page shows the current stage, `completed`/`total` and the path of the event, with a
  Cancel button that sets the call's cancel flag. The `cancelled` error is shown as a neutral
  "Stopped; continue any time" with a Resume button that re-sends the same request (§3.1:
  re-sending resumes), never as a failure. Interrupted work is shown from the batch's phase and
  flags after a restart (Q31: nothing resumes on its own).
- **Closing the window** (Q30): with calls in flight, the user confirms; the GUI then cancels
  every call and waits for them in a modal "Finishing the current step" dialog, which offers
  "Quit now" (process exit, like the CLI's second Ctrl+C: every step is idempotent). With a run
  that is not final, the close dialog says that the cloud machine keeps working, stops itself
  at its time limit (worker watchdog and the reaper, §5.2), and is followed again at the next
  start. The backend's `ports.state` is closed last.
- **Errors.** An `ErrorResponse` is shown where the action was started (a banner in the page,
  or a dialog for a modal action): the message, then a collapsed "Details" section with the
  code, the details as a table, and "Open log folder". A small table maps codes that have a
  fix in the GUI to a button (`credentials_missing`/`credentials_invalid` → settings page,
  `cloud_not_set_up`/`cloud_setup_outdated` → cloud setup, `cleanup_pending` → the batch named
  in the details, `app_busy` → Retry); that table is presentation, the decision stays the
  backend's. `internal_error` adds "see the log". Unknown codes render with the generic layout,
  so a new backend code never breaks the GUI.
- **Texts.** English only for now (Q32); every user-visible string of an area lives in its
  view-model or `view.py`, not in the backend responses' wording, except the backend's
  `message` fields, which are shown as they are.
- **Layout** (Q33): a main window with a left navigation of four pages: "New job" (folder tree,
  filters, selection, languages), "Jobs" (history list and the job page with review, upload,
  download, retry and cleanup), "Cloud" (start transcription, the current and last runs, cloud
  machines), "Settings" (languages, file types, ffmpeg, placement defaults, accounts, cloud
  setup, about).

### CLI

- **Still JSON first.** `transcribe-ui run <request.json>` stays the CLI for every request
  (requirements: the surface is too complex for flags); every request action has its GUI page
  and is reachable from the CLI only through `run`. M6 adds ergonomics, no new semantics:
  - `run -` reads the request from stdin (same UTF-8 rules), so a script or an LLM can pipe it.
  - `run --progress text` writes one human-readable line per event to stderr instead of NDJSON
    (default stays `ndjson`, so scripts keep working).
  - `credentials`: prompts for each credential without echo (`getpass`; Enter skips a field),
    builds a `StoreCredentialsRequest` and prints its response like `run`, so secrets never sit
    in a file or in shell history. Refused with `invalid_arguments` when stdin is not a
    terminal (use a request file there).
  - Confirming from the CLI: the `needs_confirmation` response names each `field` and its
    `set_to`; the user adds them to the request file and runs it again (documented in §3.1).
  - `gui` starts the GUI; the bare executable does the same (A20).

### Testing

- **View-model tests** (most GUI tests; no display needed): a view-model on `SyncExecutor`
  over a seeded backend (`support.fakes.seeded_ports`, moto, the fake Runpod API), driven like
  a user (set filters, tick folders, confirm), asserting the requests it builds and the display
  data it derives.
- **Request goldens.** The request a view-model builds for a scripted widget state is written as
  JSON to `apps/desktop/tests/golden/gui_<area>_*.json` and compared byte for byte (normalised
  like responses, §7). The same documents then run through the parity runner's backend and CLI
  legs, so a GUI-built request is proven to be a valid CLI request with the same response.
- **Bridge parity.** The parity runner gets a third leg, `gui`: the request goes through
  `QtExecutor` on its thread pool (pytest-qt `qtbot.waitSignal`), and the response, progress
  events and their order must equal the backend leg's. Run for one request of every area.
- **Widget smoke tests** (pytest-qt): each page builds, binds to its view-model, a few clicks
  reach the expected request; the selection tree model passes `QAbstractItemModelTester`; the
  close-with-calls-in-flight path, cancel and resume, the `app_busy` notice and the start-up
  sequence are exercised with a scripted executor. No screenshot or pixel comparison (fonts and
  styles differ by OS).
- **CI.** The GUI tests run in the desktop target on `ubuntu-24.04` and `windows-2025` with
  `QT_QPA_PLATFORM=offscreen` (set in `conftest.py` with `setdefault`, so a developer can
  override it to see the windows); no Xvfb. The Ubuntu leg installs the libraries Qt loads even
  offscreen (M6.2 settles the minimal apt list, expected `libegl1`, `libgl1`, `libxkbcommon0`,
  `libfontconfig1`, `libdbus-1-3`). macOS gets the GUI first in M8's build smoke run.
- **Lint.** Qt item-model and event overrides must keep Qt's names (`rowCount`, `data`,
  `index`, `paintEvent`, ...): `.flake8` per-file-ignores for `gui/**/models.py` and
  `gui/**/view.py` limited to `N802` and `WPS110` (Qt API names), with a comment; everything
  else is fixed, not suppressed. mypy strict uses PySide6's own stubs; an override is added only
  for a stub gap found in practice, with the reason. Spellcheck words (`qt`, `pyside`, ...) are
  added to `whitelist.txt` by the part that first needs them.

## 2. Request coverage

Every request action of `api/classes.py` and where the GUI uses it. Every action is also a CLI
request through `transcribe-ui run <request.json>` (or `run -`); the CLI column names only the
extra entry points M6 adds.

- Settings and accounts (M6.3):
  - `get_app_info`: Settings → About; the window title's version.
  - `get_settings`: start-up; Settings pages.
  - `update_settings`: Settings → Save (the whole document; `invalid_request` details shown per
    field).
  - `store_credentials`: Settings → Accounts → Save (only the fields the user changed). CLI:
    also `transcribe-ui credentials`.
  - `credentials_status`: start-up (first-run notice); Accounts page (set / from environment /
    missing, never values).
  - `check_credentials`: Accounts → Test.
  - `cloud_setup_status`: Settings → Cloud setup (missing, outdated, duplicated objects; Q29's
    volume ids listed).
  - `setup_cloud`: Cloud setup → Set up / Update (long request with progress).
- New job (M6.4):
  - `scan_tree`: New job → Choose folder (scan options from the settings; warnings listed).
  - `preview_selection`: every tick, untick and filter change (`latest` channel, the scan's
    `scan_id` passed); the tree's tri-state and the totals come from its response.
  - `create_batch`: New job → Create job (languages for the whole selection, other languages
    per file; the existing-language confirmation of the requirements).
  - `edit_batch`: Jobs → a composing job → Edit selection (opens New job on the stored scan
    options and operations), then Save.
- Jobs (M6.5):
  - `list_batches`: Jobs list (phase, counts, languages, `cleanup_pending`, `manifest_held`,
    `audio_deleted` badges); "Show hidden" sets `include_hidden`.
  - `get_batch`: the job page (items, jobs, statuses, `result_error`).
  - `set_batch_hidden`: job page / list → Hide, Show.
  - `delete_batch`: job page → Delete (composing or reviewing; GUI confirmation).
  - `start_review`: job page → Continue to review.
- Review and upload (M6.8):
  - `review_batch`: Review page (probing progress; the language and folder filters of the main
    view, `latest` channel).
  - `resolve_review`: Review page → Apply choices (transcribe or extract per embedded subtitle;
    the audio track per multi-track file).
  - `exclude_items`: Review page and job page → Remove from job (GUI confirmation).
  - `run_upload`: Review page → Upload; job page → Resume upload (progress, Cancel, Resume).
- Cloud (M6.6):
  - `plan_launch`: Cloud → Start transcription (the plan: jobs, audio length, cost range,
    unknown and unreadable batches).
  - `launch_worker`: the start dialog → Start (wait for a machine, 5 min-24 h, default 1 h;
    test mode under "Advanced"; `set_to` copied into `confirm_fingerprint`; a changed plan
    re-opens the dialog with the new one).
  - `cancel_worker`: Cloud → Cancel while waiting for a machine; Stop while starting or
    transcribing (Q34).
  - `refresh_status`: start-up, the poll while a run is not final, Refresh now.
  - `reconcile_cloud`: start-up; Cloud → Cloud machines → Check.
  - `terminate_pod`, `cancel_queued_pod`: Cloud machines list → Terminate / Cancel on a straggler
    or overdue entry (backend confirmation).
  - `list_runs` (new, M6.1): Cloud page history (last runs, outcome, worker log link).
- Download (M6.9):
  - `plan_download`: job page → Download (strategy and options pre-filled from the settings'
    placement defaults; the plan table with outcomes, collisions and "not finished yet").
  - `run_download`: Download dialog → Download (overwrite confirmation; progress, Cancel,
    Resume; `failures` listed).
  - `export_custom_plan`: strategy Custom → Export plan (save-file dialog → `path`).
  - `import_custom_plan`: Custom → Import plan (open-file dialog → `plan_path`; `check_only`
    first to show validation, then the import).
- Retry and cleanup (M6.10):
  - `create_retry_batch`: job page → failed and no-speech files ticked → Retry (progress while
    the audio is copied; opens the new job).
  - `cleanup_cloud`: job page → Clean up cloud (audio only / everything; backend
    confirmations); "Repeat cleanup" on a batch with `cleanup_pending`; start dialog → an
    unknown batch → Delete from cloud (Q28).

Requirements user flows and the parts that cover them: file selection with tree, filters and
languages (M6.4); review step (M6.8); conversion and upload, interruptible and resumable (M6.8);
job history with hidden jobs (M6.5); start, wait, cancel and follow the cloud machine with job,

M6.10 retries); every download option and the custom JSON plan (M6.9); cloud cleanup after the
download and at any time (M6.10); credentials and cloud setup (M6.3).

## 3. Parts

Every part is one PR that leaves `main` mergeable and green, owns its `gui/<area>/` sub-package
and its tests, adds its golden files under its own prefix, and moves its decisions from §1 into
`architecture.md` §3.1 (a "GUI" subsection grows part by part) or `tooling.md`. Shared hot spots
are one-line additions: page registration in `gui/shell.py`, `whitelist.txt`, a paragraph in
`architecture.md`. Only M6.1 changes `api/classes.py`, `api/routes.py` and existing goldens.
"High effort" means the implementing agent runs with `effort: "high"` (CLAUDE.md "Effort").

## 5. Risks

- **One executable for GUI and CLI on Windows** (A20): a console-subsystem exe started from
  Explorer flashes a console before it detaches; a windowed exe would break the CLI's stdout and
  exit code. Settled before M8 builds it; M6.2 implements the default behind a port.
- **Qt on CI**: the offscreen platform still loads EGL/GL, xkbcommon and fontconfig on Linux;
  Windows offscreen has fewer gaps. M6.2 settles the apt list early; a missing library fails
  every GUI test at import, not silently.
- **Thread safety of the ports** under concurrent GUI calls: the backend is documented
  thread-safe (§3.8, the scan cache is locked), but no M5 test ran a scan, a refresh and an
  upload at the same time. M6.2's bridge tests run mixed requests in parallel on the seeded
  backend.
- **Shutdown and lock waits**: a call can sit in the runs lock's 30 s wait or in Runpod retries
  when the user closes the window. "Quit now" is the escape; every step is idempotent, so a
  forced exit loses no state (as with the CLI's second Ctrl+C).
- **Preview latency on large trees**: `preview_selection` runs the filters over every file of
  the cached scan on each click. Latest-wins cancellation keeps the GUI responsive; if a 20 000
  file tree is still slow, the backend's preview gets faster (a backend change in M6.4), not a
  GUI-side shortcut.
- **mypy strict and WPS with PySide6**: signal typing and Qt override names cause friction;
  limited per-file ignores (§1 "Lint") are the budget, anything beyond goes to the architect.
- **Backend API drift**: M6.1 changes response shapes (`actions`, `set_to`, `name`) that the CLI
  goldens show; done once, before the GUI parts, so later parts do not regenerate shared
  goldens.
- **Polling cost**: one `refresh_status` every 30 s reads two Runpod lists; a 24 h wait for a
  machine is about 5 800 list calls. Runpod's rate limits are not documented in
  `research/runpod.md`; the client honours 429 `Retry-After` and the single-flight poll never
  piles calls up. M7 observes it on a real run.
