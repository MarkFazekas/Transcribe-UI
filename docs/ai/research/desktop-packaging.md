# Desktop app research (2026-11-26)
Legend: [V] verified from a fetched/searched source (URL given); [I] inference / prior knowledge, verify before relying.

## 1. GUI toolkit
Recommendation [I]: PySide6 (Qt Widgets, QTreeView + custom QAbstractItemModel with lazy fetchMore/canFetchMore and Qt.ItemIsUserTristate-style logic done in the model).
- [V] PySide6 6.12 is released; its notes list host Python 3.10-3.14; 6.12 wheels are cp310-abi3 (https://www.qt.io/blog/qt-for-python-release-6.12-is-here , https://doc.qt.io/qtforpython-6.11/release_notes/pyside6_release_notes.html). 6.10.0 on PyPI required Python <3.14 (https://pypi.org/project/PySide6/6.10.0/). => use PySide6 >= 6.11/6.12 for Python 3.14.
- [I] Qt model/view is virtual: only visible rows are painted, so 10^4-10^5 nodes is fine if the model is lazy and tri-state is computed in the model (store checked state on leaves, derive parent state, cache counts). QTreeView is the only option here that scales without hand-rolled virtualization.
- [I] Typing: PySide6 ships .pyi stubs; mypy strict works but with some Any/overload friction (signals typed as SignalInstance). Textual is well typed but a TUI (no native tree-of-files UX users expect; fine for power users). Tkinter ttk.Treeview: no native tri-state, no model; poor at 50k nodes without hand lazy-loading; typeshed stubs good. NiceGUI/Flet/pywebview: web/Flutter rendering; ui.tree in NiceGUI (Quasar) is not virtualized, heavy for 10^4+ nodes; Flet adds a Flutter runtime; pywebview needs system WebView2/WebKitGTK (Linux dependency pain). Bundles smaller than Qt but tri-state at scale is DIY.
- [I] Testing: pytest-qt (QtBot, offscreen via QT_QPA_PLATFORM=offscreen; xvfb on CI Linux), plus QAbstractItemModelTester for the model. Background work: QThreadPool/QRunnable or QThread + signals; keep business logic in plain asyncio/threads and bridge with signals (queued connections).
- LGPL [I, not legal advice]: PySide6 is LGPLv3 (Qt Essentials/Addons also commercial). A one-file PyInstaller bundle is a form of static-ish packaging; LGPL requires users be able to replace the Qt libs. In onefile the Qt libs are extracted to a temp dir as separate .dll/.so files so relinking is feasible; ship LGPL text, attribution, and offer source/instructions (Qt docs on this: https://doc.qt.io/qtforpython-6/commercial/index.html). Nuitka onefile/ PyInstaller onefile both keep Qt as separate shared libs; keep app source open or provide rebuild path. Avoid Qt modules that are GPL-only (e.g. Qt Charts/Data Viz/ some addons) -- check module licences.
- Size [I]: PySide6 onefile ~60-150 MB if you exclude unused modules (QtWebEngine is the monster; avoid). Startup 1-3 s onefile.

## 2. Single-file packaging
Recommendation [I]: PyInstaller --onefile (Windows, Linux); on macOS a onefile binary works but a .app (onedir inside a zipped .app) is the sane macOS shape; if "single file" is strict, ship the raw Mach-O binary (works from Terminal; double-click opens Terminal).
- [V] PyInstaller added Python 3.14 support in 6.15.0 (2025-08-03, #9192); latest stable listed is 6.22.0 (2026-08-08) (https://pyinstaller.org/en/stable/CHANGES.html). Python 3.15 betas unsupported.
- [V] Nuitka 4.0 stable (2026-04-22); PyPI says Python 3.4-3.14 supported (https://nuitka.net/posts/nuitka-release-40.html , https://pypi.org/project/nuitka). Qt docs show Nuitka onefile with PySide6, but note a macOS bundle crash caveat; pyside6-deploy default switched from onefile to standalone in 6.12 (https://doc.qt.io/qtforpython/deployment/deployment-nuitka.html). Not found: explicit PySide6+Nuitka 4.0+3.14 test statement.
- [I] Nuitka: faster runtime, much slower builds (C compile; CI 10-30 min with Qt), fewer AV false positives than PyInstaller reputedly but still onefile extraction; license: Nuitka commercial plugins optional, core Apache. PyInstaller: fast builds, huge community hooks (keyring, pydantic, PySide6 included), simpler. briefcase: produces installers/.app/.msi/AppImage-ish, not single exe. PyApp (Rust bootstrapper): downloads Python at first run - needs network, not self-contained.
- [I] Onefile startup: extracts to %TEMP%/_MEIxxxx each launch (~1-3 s for Qt, more with AV scanning). Mitigate: --noupx (UPX raises AV hits), exclude unused Qt modules, lazy imports.
- [I] Windows AV: onefile PyInstaller bootloader is a frequent false positive; mitigate by building bootloader from source (or latest), no UPX, version info resource, code signing (Azure Trusted Signing / SignPath OSS), submit to Microsoft for analysis.
- [I] macOS: unsigned binaries downloaded via browser get com.apple.quarantine -> Gatekeeper blocks; users must `xattr -d com.apple.quarantine` or right-click Open. Apple Silicon requires at least ad-hoc signature (PyInstaller does ad-hoc by default; codesign_identity to override). Real distribution needs Developer ID + notarization (notarytool; can notarize a zip/dmg, cannot staple a bare binary). Files downloaded via `gh`/curl are not quarantined.
- [V] Runners: macos-13 retired (Dec 2025); Intel label is macos-15-intel (supported to ~Aug/Fall 2027); macos-26 (arm64) GA 2026-02; macos-14 retirement announced (https://github.blog/changelog/2025-09-19-github-actions-macos-13-runner-image-is-closing-down/ , https://github.blog/changelog/2026-02-26-macos-26-is-now-generally-available-for-github-hosted-runners/ , https://github.blog/changelog/2026-10-01-github-actions-macos-14-runner-image-retirement). Use macos-15 (arm64) + macos-15-intel. [I] universal2 requires all deps (PySide6, pydantic-core, etc.) as universal2 wheels; PyInstaller --target-arch universal2 often fails for that reason; ship two binaries instead. Python.org dropped Intel Mac to tier 2 (https://discuss.python.org/t/dropping-intel-mac-to-tier-2/102100).
- [I] Linux glibc: build on the oldest ubuntu you support (ubuntu-22.04, glibc 2.35; binary runs on >=22.04). Check current availability of ubuntu-22.04 label in your org (22.04 ARM ended Sept 2026 per endoflife.date; x64 still listed at time of search but confirm). Qt xcb needs libxcb-cursor0 etc. on target machines (document it); Wayland: set QT_QPA_PLATFORM fallback.
- Recommended Python: 3.13 (safest for wheels/PyInstaller/PySide6); 3.14 workable with PySide6>=6.11 and PyInstaller>=6.15. [I]

## 3. ffmpeg/ffprobe
- [V] static-ffmpeg (PyPI) provides both ffmpeg and ffprobe, but downloads binaries at first run (https://pypi.org/project/static-ffmpeg/2.7) [I: download-at-runtime means not bundled in the wheel; can pre-run in CI to populate]. imageio-ffmpeg: ffprobe NOT confirmed (https://pypi.python.org/pypi/imageio-ffmpeg); [I] it ships ffmpeg only.
- [I] Recommendation: in CI download pinned static builds per platform and embed via PyInstaller --add-binary; at runtime resolve via sys._MEIPASS, extract (onefile already extracts) and chmod +x. Sources: BtbN/FFmpeg-Builds (win64/linux64; offer LGPL "-lgpl" variants), johnvansickle (GPL static, linux), evermeet.cx (x86_64 only, ffmpeg and ffprobe separate zips) / osxexperts.net (arm64), or Homebrew-free alternatives. Pin version + SHA256 in repo.
- [I] Licensing: GPL builds (libx264/x265) make the combined distribution subject to GPL obligations for ffmpeg itself (separate executable invoked as subprocess = aggregate, but you must provide ffmpeg source offer). If you only need remux/probe/audio extraction/AAC/opus decoding, use LGPL builds (BtbN lgpl) and avoid --enable-gpl/nonfree. Size: ~80-130 MB per ffmpeg+ffprobe pair uncompressed (ffmpeg and ffprobe ~each 70-100 MB static); onefile grows to 150-300 MB. Alternative: allow PATH override + download-on-first-run to user data dir (smaller exe, needs network; [I] my preference if size matters). Use `--ffmpeg-path` config override either way.

## 4. Cloudflare R2 + boto3
- [V] Endpoint https://<ACCOUNT_ID>.r2.cloudflarestorage.com, region_name="auto" (https://developers.cloudflare.com/r2/examples/aws/boto3/). Empty region and us-east-1 alias to auto (https://developers.cloudflare.com/r2/api/s3/api/).
- [V] botocore >=1.36.0 enables default integrity checksums; Cloudflare status/docs state default configs can produce "header ... not implemented" errors; workaround is WHEN_REQUIRED (https://www.cloudflarestatus.com/incidents/t5nrjmpxc1cj , https://docs.aws.amazon.com/sdkref/latest/guide/feature-dataintegrity.html). Cloudflare's own S3 API table lists CRC-32/CRC-32C/SHA-1/SHA-256/CRC-64NVME checksums (https://developers.cloudflare.com/r2/api/s3/api/) -- docs and status note conflict, so the 2026 status of default behaviour is UNCERTAIN; I could not find a Cloudflare statement that it's fixed. [I] Be defensive: always set
  `Config(request_checksum_calculation="when_required", response_checksum_validation="when_required", signature_version="s3v4", s3={"addressing_style":"virtual"|"path"})` and add an integration test against a real/test R2 bucket (or moto won't catch this).
- [V] R2 multipart: re-uploading a part number replaces it; doesn't list part-size limits on that page. [I] Known limits: min part 5 MiB (except last), parts of equal size recommended, max 10,000 parts, object max ~5 TiB; use TransferConfig(multipart_threshold=64MiB, multipart_chunksize=64MiB, max_concurrency=8, use_threads=True). ETag of multipart != MD5; don't verify via ETag.
- [V] Unsupported on R2: object tagging, ACLs, versioning, SSE-KMS, object lock, bucket policy (same URL). Presigned URLs work via boto3 generate_presigned_url (SigV4, S3 domain only, not custom domains) [I; page doesn't mention them].
- Library choice [I]: boto3 + types-boto3[s3] (or boto3-stubs[s3]) gives the best typing and TransferManager; heavy (~15 MB) but PyInstaller handles it. obstore (Rust, typed, async, fast, small, supports R2 via S3Store) is the strongest alternative if you do not need TransferManager/presign extras (it has presign support) -- not verified in this pass. minio-py is typed too but R2 support is "S3-compatible" without Cloudflare testing; aioboto3 is untyped-ish wrapper. Pick boto3 for safety, obstore if size/async priority.
- [V] Tokens: permissions Admin R/W, Admin Read, Object R/W, Object Read; only Object permissions can be scoped to specific buckets; docs mention NO prefix restriction (https://developers.cloudflare.com/r2/api/tokens/). Conclusion: a token can be limited to a single bucket, NOT to a prefix. [I] Prefix isolation requires a Worker/presign broker or separate bucket. Note Object R/W token with bucket scope still can't create buckets; check `list_objects_v2` works for existence checks rather than head_bucket.

## 5. keyring
- [V] keyring discovers backends via setuptools entry points in package metadata; PyInstaller ships hook-keyring.py that collects keyring.backends submodules and metadata; without metadata it falls to the `fail` backend raising "No recommended backend was available" (https://sources.debian.org/src/pyinstaller/6.18.0%2Bds-1/PyInstaller/hooks/hook-keyring.py). Fix [V/I]: ensure --copy-metadata keyring and --collect-submodules keyring.backends (plus for Linux: secretstorage, jeepney; for Windows: pywin32-ctypes is a keyring dep).
- [I] Backends: Windows Credential Locker via Windows Credential Manager (keyring.backends.Windows.WinVaultKeyring); macOS Keychain (macOS.Keyring, uses Security framework via ctypes in modern keyring); Linux SecretService (needs D-Bus session + gnome-keyring/KeePassXC unlocked) and KWallet. Headless Linux/WSL: no D-Bus secret service -> keyring raises NoKeyringError; fall back options: (a) keyrings.alt EncryptedKeyring/PlaintextKeyring (prompt for passphrase; plaintext is poor), (b) env vars, (c) CLI flag. Design: Credential store protocol with keyring impl + env-var impl; surface a clear error.
- [I] Windows credential blob limit 2560 bytes (CRED_MAX_CREDENTIAL_BLOB_SIZE); keyring's WinVault stores UTF-16 so effective ~1280 chars; R2 access key id (32) + secret (64) fit fine; store as two entries or one small JSON. Don't store large JSON blobs.
- [I] macOS: unsigned/ad-hoc binary writes to the login keychain; each re-signed rebuild changes code identity so users may get access prompts again.

## 6. App data and batch state
- [I] platformdirs: user_data_dir (durable app data/batch records), user_state_dir (logs, resumable state; on Windows/macOS it falls back to data dir), user_cache_dir (ffprobe results, thumbnails), user_config_dir (settings). Pass appname/appauthor explicitly; use ensure_exists.
- [I] State: SQLite (stdlib sqlite3, WAL mode, `PRAGMA synchronous=NORMAL`, transactions) is the best fit for tens of thousands of file rows with per-file upload status, crash-safe and concurrent-reader friendly, and built-in locking. Use JSON only for small manifests/exports: write temp file in same dir, flush+os.fsync, os.replace() (atomic on Windows and POSIX); lock with `filelock` for single-instance. Store ULIDs as batch IDs; each batch = one DB file or a table.

## 7. ULID
- [V] python-ulid (mdomke) latest changelog 4.2.0 dated 2026-11-17, Python 3.15 support added, 3.10 dropped; Pydantic v2 protocol added in 3.2.0 (optional extra `python-ulid[pydantic]`) (https://python-ulid.readthedocs.io/en/latest/changelog.html , https://github.com/mdomke/python-ulid). Also pydantic-extra-types has a `ULID` type based on python-ulid (https://pydantic.dev/docs/validation/2.9/api/pydantic-extra-types/pydantic_extra_types_ulid/). Requires Python >=3.11 now [I from "dropped 3.10"].
- [I] ulid-py is unmaintained; python-ulid is typed (py.typed) and maintained -> choose python-ulid. Alternative: stdlib uuid.uuid7() exists in Python 3.14 (time-ordered) if you don't need ULID format [I].

## 8. GitHub Actions
- [V] actions/upload-artifact v7.0.0 (Feb 2026) added `archive: false` ("If 'false', only a single file can be uploaded"); `name` ignored, artifact takes the file's name; fails if glob matches multiple files (https://github.com/actions/upload-artifact , https://github.com/actions/upload-artifact/releases). So bare exe artifacts are possible per-platform (unique filenames needed, e.g. app-windows-x64.exe, app-macos-arm64, app-linux-x64).
- [I] Artifacts need login to download and expire; for public delivery use a GitHub Release: `gh release upload --clobber` or softprops/action-gh-release on a rolling tag (e.g. `latest`) or per-commit tag `build-${{ github.run_number }}`. Needs `permissions: contents: write`. Executable bit is lost through artifacts/zip; Release assets keep bytes but not mode -> document chmod +x (or tar.gz for Linux/macOS, which violates "bare").
- [I] Workflow skeleton: on: push: branches: [main]; paths: ['src/**','pyproject.toml','uv.lock','.github/workflows/build.yml', 'packaging/**']; no pull_request trigger; concurrency group cancel-in-progress; matrix [windows-latest, macos-15 (arm64), macos-15-intel, ubuntu-22.04]; astral-sh/setup-uv; `uv sync --frozen`; `uv run pyinstaller ...`; smoke test the binary (`--version`) before upload; upload with archive:false then a final release job (needs: build) downloads and publishes. Pin actions by SHA.
- Caveat: paths filter on push only applies to push events; workflow_dispatch for manual rebuilds.
